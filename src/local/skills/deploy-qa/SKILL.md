# deploy-qa — QA every issue a deploy shipped

Generic procedure. It holds no environment values: the profile is the environment skill the caller names (e.g. `acme-env:post-deploy` names `acme-env:staging-qa`) — read every value below from that skill's `## Environment` and `## Policy` sections. This skill decides range, admission, order, lock, carry-over, and posting. It never deploys, merges, reverts, pushes, or moves an issue to done.

Sub-skills: `$local:qa-issue` (one issue) and `$local:qa-report` (HTML + PNG). Through the SDK Skill tool they are `zworkflow:qa-issue` and `zworkflow:qa-report`.

## GitHub calls
Read GitHub through its REST API with curl; this works inside a sandboxed session. The `gh` CLI's own network calls (`gh api`, `gh pr …`, `gh run …`, `gh repo …`) can fail inside a sandbox (TLS verification), so do not use them. `gh auth token` only reads the stored token and works there. A **GitHub call** is:

```bash
curl -fsSL --connect-timeout 10 --max-time 30 -H "Authorization: Bearer $(gh auth token)" -H "Accept: application/vnd.github+json" "https://api.github.com/<path>"
```

- Write the whole form in every shell call, both timeouts included; shell state does not carry over between calls. Read fields with `jq` (e.g. `… | jq -r .status`).
- `-f` turns an HTTP error into a non-zero exit, so a call that exits 0 got a success response.
- Paging: add `per_page=100&page=N` and request N = 1, 2, … until a page holds fewer than 100 items (or follow the `rel="next"` URL of the `Link` response header, dumped with `-D <file>`, until there is none). A listing is complete only when paging reached that end (and, where the response has `total_count`, the items read add up to it). A call that failed or timed out, or paging that stopped early, leaves the listing incomplete — never read it as empty or complete.

## Args
- `repo`, `target`: the deployed repo and the branch the deploy merged into, exactly as the deploy reported them.
- `before`, `after`: the target SHA before the deploy and the deployed merge commit. The range is `before..after` — nothing else (no ledger).
- `env`: the profile skill (e.g. `acme-env:staging-qa`); absent → the calling skill. The same name is passed to `qa-issue` as `env=`.
- `--preflight`: readiness check, see below. No writes.
- `--confirm`: run the deploy confirmation of step 1 only, for `repo`, `target`, and `after` (both ways, the same budget), and write nothing: no lock, no run directory, no tracker read or write, no post. Answer with exactly one line: `confirmed`, `unconfirmed: <reason>`, or `failed: <run> concluded <conclusion>`. Budget spent → `unconfirmed: not confirmed in time`; a profile entry step 1 needs is absent → `unconfirmed: missing: <fields>`. The deploy workflow asks this for every repo with QA before it QAs any repo, and reports the answer as that repo's deploy confirmation.
- `--plan-only`: steps 1–5 without the run directory, post the admission table, stop. No lock, no tracker writes, no QA.
- `keys=<K,…>`: restrict the target set to these keys; they still go through admission. Used for re-runs.
- `decisions=<gate file>`: the run gate the requester answered (step 5.5). An environment skill that wraps this one passes it through unchanged. The requester answers in the calling thread, so the session that asked receives the answer, records it, and passes this; the run then resumes from step 5.5 instead of asking again. A reply from anyone other than the requester is not an answer.

## Profile (required; preflight checks every entry)
- `applies[]`: `{repo, target}`.
- `repos[]`: `owner/repo` + `integrationBranch`. The deployed repo and every related repo.
- `deploy`, per repo: the CD workflow for the target branch, or an explicit statement that the repo deploys without one; and `runningSha` — how to read the commit that repo is running (a health URL field, a server-tools command, …).
- `keyPattern`.
- `tracker`: site; per project the state IDs `qa` and `done` and the transition IDs `toQa` and `toDone`; `carryLabel`; comment conventions.
- `admission` (ordered rules) · `doneConditions` · `lockDir` · `checkpointEvery`.
- `qaEnv`: the adapter commands `open`, `eval`, `screenshot`; `screenshotsDir`; health URL(s); test-account references. Optional, read by the precondition gate (absent = those preconditions are `missing`, never a `missing:` answer here): `qaEnv.accounts`, `qaEnv.writes`, `qaEnv.seed`, `qaEnv.logs` — see `qa-issue` Profile fields.
- `report`: thread publishing (serve command or upload method; uploading the files with the session's Slack file tool is one) and, if any, the summary channel.

Any entry absent → reply with exactly one line `missing: <field,…>` and stop. Never guess a value or take one from another host. Account entries are references to where credentials live; never print, comment, or file-name a credential.

## Preflight (`--preflight repo=… target=…`)
Reply with exactly one line. Write nothing, except that the `lockDir` and screenshots-directory checks may create those directories and one probe file each, which they remove:
1. `applies` absent → `missing: applies`.
2. `{repo, target}` not in `applies` → `not-applicable`.
3. Any other profile entry absent → `missing: <fields>` (QA cannot run).
4. Tool checks: a GitHub call to `repos/<owner/repo>` returns 200 for every repo; one tracker read per project; `command -v` for each adapter executable (do not open a page); `lockDir` is a writable directory, or does not exist yet and its parent allows creating it (test with `mkdir -p`, then create and remove one probe file in it — a sandbox can refuse the write even when the permissions allow it); the screenshots directory (`qaEnv.screenshotsDir`) is writable the same way; the bundled files resolve: `test -f` on `$CLAUDE_PLUGIN_ROOT/skills/qa-report/scripts/mask.mjs`, `…/qa-report/scripts/build.mjs`, `…/qa-issue/scripts/gate.mjs`, and `…/html/renderer/render.mjs`. `$CLAUDE_PLUGIN_ROOT` is the zworkflow plugin root, two directories above this skill's base directory (`…/skills/deploy-qa` → `…`); shells usually do not set it, so write the absolute path.
   - Any GitHub, tracker, or bundled-file check fails → `missing: <checks>` (the range, the tracker, or the evidence tooling cannot be used).
   - Only adapter, screenshots-directory, and/or `lockDir` checks fail → `partial: <checks>`; the run uses Reduced mode.
5. Otherwise → `applies`.

## Reduced mode (preflight `partial: <checks>`)
A full run repeats the adapter, screenshots-directory, and `lockDir` checks before step 1 and reduces itself for each one that fails:
- **`lockDir` not writable** → take no lock and QA no issue: no `qa-issue` call, no tracker transition, no carry-over write, no heartbeat. Still do steps 1–5 read-only (confirm the deploy, range, PRs, admission) and the step 9 report. `R` is then a new directory this session can write (create it and confirm one write before use); it holds this run's report input only and nothing resumes from it. Every target key gets outcome `not-run`, reason `QA lock unavailable`; keys admission already decided (deferred, report-only, already passed) keep that outcome. No `R/<KEY>.json` exists, so step 9 builds no `issues` (no `jq -s` over `R/<KEY>.json`): write `R/report/report-input.json` with `issues: []`, every key once in `nonQa` — a target key as `{key, status: "not-run", reason: "QA lock unavailable"}`, any other key with its admission status and reason — and the same outcome and reason for every key in `outcomes`; `meta`, `links`, `bodyMentions`, and `excludedPrs` as usual. `qa-report` accepts this shape and renders one row per key. The final status is `deployed, QA incomplete: QA lock unavailable`.
- **An adapter executable missing, or the screenshots directory not writable** → QA the issues without screen evidence: invoke `qa-issue` with `qa=high` instead of `max`, and without `transition=done` (so without the exclude lists, which only feed `doneConditions`): `$local:qa-issue <KEY> qa=high env=<profile skill> mergeShas=<owner/repo:sha,…> runDir=<R> decisions=<gate file>` (step 5.5 plans with `qa=high` too). A missing adapter or screenshots directory is a tooling problem: it is never put to the requester as a precondition. `max` is the level that covers every changed screen; never pass it while the browser adapter is missing. Without `transition=done`, `qa-issue` never moves an issue to done or back to in-progress; its own profile checks decide what it can still run. Outcome for each such key = `partial`, reason `<adapter> unavailable` or `screenshots directory unavailable` (a `fail` stays `fail`: qa-issue commented it and notified the assignee, and the issue keeps its state).
- The report's status line names every check that failed.

## Excluded PRs (one rule, used everywhere)
`excludeHeads` = `main,deploy/,release/` — an entry ending in `/` is a prefix, any other entry an exact name (so `main` does not exclude `maintenance/…`). `excludeBases` = every target in `applies` plus every base branch starting with `deploy/` seen in the step-3 listings (exact names). A PR is excluded when its head matches an `excludeHeads` entry or its base is in `excludeBases`. Excluded PRs never count (no key, no open PR, no mergeSha) and are listed in the report. Pass both lists to `qa-issue` unchanged, so its no-open-PR check applies the identical rule.

## Lock (full runs only; acquire before step 1; none in Reduced mode for `lockDir`)
`L` = `<lockDir>/lock`. Token = `<channel>:<thread_ts>` of the calling thread, no whitespace. `startTime` = acquisition time, UTC `YYYYMMDDTHHMMSSZ`. `L/owner` = `<token> <startTime>`. Use absolute paths; the shell's working directory resets per call.
- **Mine** = both fields of `L/owner` equal my token and the `startTime` this run recorded when it acquired. A new invocation has no recorded `startTime`, so a live lock is never mine — even one from the same thread.
- **Acquire:** `mkdir L` → write `L/owner`, `touch L/heartbeat`, then post the run's first line to the calling thread: `deploy-qa started <token> <startTime> <repo> <before7>..<after7>`. A resumed run reads its `startTime` back from that post.
- **Busy** (exists, not mine): wait in this session, re-checking every 5 min for up to 60 min, touching nothing. Still busy → end `deployed, QA incomplete: lock busy` + re-run args.
- **Stale** (heartbeat mtime — absent → mtime of `L` — older than 2 h): never remove or move it yourself; a reclaim cannot be made safe against a concurrent acquire. End `deployed, QA incomplete: stale lock` naming `L/owner` and the heartbeat age, with the re-run args, and say that a person removes `L` after confirming that owner's run is gone.
- **Heartbeat** at every step and after every issue: read `L/owner`; mine → `touch L/heartbeat`. If you no longer hold your `startTime` (e.g. after context compaction), re-read it from your start post or from `R`'s directory name before judging. Not mine or gone → stop all work at once and end `deployed, QA incomplete: lock lost` + re-run args. Never touch another owner's heartbeat.
- **Release** on every exit path: `rm -rf L` only if mine.

## Outcomes (one per target key)
- **pass** — qa-issue verdict `pass`, `trackerComment` set, and `statusTransition` has `performed` and `verified` true and `to` = the done state; or **already passed**: a pass comment naming the same mergeShas and the issue in the done state now.
- **fail** — verdict `deploy_fail` with `trackerComment` set (qa-issue already commented, notified, reverted state).
- **report-only** — decided by admission, with its reason.
- **open** — everything else: blocked, partial, deferred, superseded, not-run, a `pass` without a verified done (reported as `blocked`, reason = `statusTransition.reason`), and any result with `trackerComment: null` (`blocked`, reason `reconcile-failed`). A key the requester skipped at the precondition gate is `deferred`, reason `precondition-skipped by <who>`. A key waiting for the requester's answer is `not-run`, reason `waiting for precondition confirmation`.

## Steps (record only facts you checked with a command)
1. **Confirm the deploy** per `deploy` for `repo`. This step owns the confirmation: the deploy workflow does not confirm a repo with QA itself — it asks this step through `--confirm` and reports that answer as the repo's deploy confirmation. A full run re-checks here; a deploy that `--confirm` already confirmed normally passes without waiting, if the current evidence still shows it deployed. Poll in the foreground every 30 s for at most 30 min in total; a failed or timed-out call is not a result, so poll again within that budget. Budget spent without a confirmation → end `deployed, QA incomplete: deploy not confirmed in time`, transition nothing.
   - When `deploy` names a CD workflow for `repo` and `target`: that workflow's run for `after` concluded `success`. Find it with a GitHub call to `repos/<owner/repo>/actions/workflows/<CD workflow>/runs?head_sha=<after>&branch=<target>` (paged), with no event filter — the run may be started by a push, `workflow_run`, or `workflow_dispatch`. An empty listing within the budget means the run is not registered yet: pending, never "no CD" — list again. While it runs, re-read `repos/<owner/repo>/actions/runs/<id>` until `status` is `completed`, then require `conclusion` = `success`. A failed run → end `deploy failed, QA not run: <run> concluded <conclusion>`, transition nothing.
   - When `deploy` declares no CD workflow: the profile's health check passes and its `runningSha` read shows `after` running.
   - Both ways also require: a GitHub call to `repos/<owner/repo>/compare/<after>...<runningSha>` piped to `jq -r .status` is `ahead` or `identical`; any extra check `deploy` lists.

   `before` must be an ancestor of `after` (compare status `ahead`), else stop; the re-run args on the reference line start from the merge base. Unconfirmed → end `deployed, QA incomplete: deploy not confirmed`, transition nothing. Record the running version as version start. Run directory `R` = `<lockDir>/runs/<startTime>-<owner/repo with / → ->-<after7>/` — one per acquisition: a resume (same `startTime`) reuses it, a re-run gets a new one and re-tests. Create it (and `R/report/`). Reduced mode for `lockDir`: `R` is the directory that section names.
2. **Commits.** GitHub calls to `repos/<owner/repo>/compare/<before>...<after>?per_page=100&page=N`, N = 1, 2, … until the commits read equal `total_commits` or a page holds no commits; keep commits with one parent. Complete only when the commits read equal `total_commits`; else end `deployed, QA incomplete: range listing incomplete`.
3. **PRs.** Range PRs: per commit a GitHub call to `repos/<owner/repo>/commits/<sha>/pulls?per_page=100`, keep merged PRs (`merged_at` set) whose base (`base.ref`) is that repo's `integrationBranch`, dedupe by number. Then, once per repo in `repos`, list open PRs (`repos/<owner/repo>/pulls?state=open`) and merged PRs into its integration branch (`repos/<owner/repo>/pulls?state=closed&base=<integrationBranch>`, keeping only PRs with `merged_at` set — a closed, unmerged PR still carries a `merge_commit_sha`), each paged as in GitHub calls. Fields: `number`, `title`, `head.ref`, `base.ref`, and for merged PRs `merge_commit_sha`. A listing is complete only when paging reached its end. Drop excluded PRs everywhere; keep reverts. Any listing that cannot be shown complete → every key is open (blocked, `PR list incomplete`), no QA.
4. **Keys.** Match `keyPattern` case-insensitively against each range PR's title and head branch, then uppercase. A key matches only when it equals the key exactly (`PROJ-12` never matches `PROJ-123`). Keys only in a PR body → report "body mention only", never transitioned. Target set = these keys + carry-over keys (issues labelled `carryLabel` that have a PR in the step-3 lists of `repos`), intersected with `keys=` when given.
5. **Admission.** Per key: tracker state and type; its open PRs (title or head key equals it); its merged PRs and mergeShas = `<owner/repo>:<merge_commit_sha>` from the step-3 merged lists, so backports and hotfixes never add one; each related-repo mergeSha contained in that repo's `runningSha` (GitHub call `compare`, `ahead` or `identical`); whether the range PRs touch only docs; whether its last merged PR is a revert; already passed (Outcomes). A pass comment while the issue is still in the qa state → target again. Apply `admission` in order, first match wins: skip / deferred / report-only + reason / target. The done state alone never counts as passed.
   `--plan-only`: post the table key | PRs | state | outcome | reason to the calling thread and stop.
5.5. **Precondition gate.** Before any QA, plan every key and ask the requester at most one question for the whole run. Skipped in Reduced mode without a lock (nothing is QA'd) and with `--plan-only` (it stops at step 5). With `decisions=<gate file>`, go to **Resume** below.
   - No target key → skip the gate. **Plan every key.** For each target key, one at a time, invoke `$local:qa-issue <KEY> qa=max env=<profile skill> --plan mergeShas=<owner/repo:sha,…> runDir=<R>` (Reduced mode for an adapter or screenshots: `qa=high`). It writes and seals `R/gate-<KEY>.json`, runs no case and writes nothing to the tracker. A key whose plan is invalid (seal exit 4) is blocked with that reason. Merge the plans into one run gate: `node "$CLAUDE_PLUGIN_ROOT/skills/qa-issue/scripts/gate.mjs" merge --out <G> R/gate-<KEY>.json …`, where `G` = `<lockDir>/gates/<owner/repo with / → ->-<after7>-<startTime>.json` (create `<lockDir>/gates/` first). The file name is the gate ID; a gate file is never overwritten.
   - `ask: false` → continue with step 6.
   - `ask: true` → post the gap table to the calling thread — per key and missing precondition: what it needs, the cases it blocks with their severity, and what the requester could provide. Build the step-9 report with every target key in `nonQa` as `not-run`, reason `waiting for precondition confirmation`, and `preconditions` from `G`, and publish it. Then release the lock only if it is mine, then ask the requester with the session's question tool (`local:UIAskUserQuestion`, one choice group: per key provide it / proceed without it / skip the key). End `deployed, QA incomplete: waiting for precondition confirmation`, with the reference line plus `decisions=<G>`. No case runs and no tracker write happens before the answer, and waiting holds no lock. The run creates no scheduler, cron job, or listener: the requester's answer in the thread resumes it. If the session has no question tool, the posted gap table is the question and the requester's reply in the thread is the answer. Adapter, screenshots-directory and `lockDir` problems never go into this question (Reduced mode handles them).
   - **Answer.** The session that receives the answer records it — `node "…/gate.mjs" answer --gate <G> --key <KEY|all> --decision provided|waived|skipped --by <who answered> --ref <message ts>`, one call per key answered differently — and invokes this skill again with the same args plus `decisions=<G>`.
   - **Resume** (`decisions=<G>`). A fresh run: new lock, new `startTime`, steps 1–5 again. For each target key, re-read its inputs (the deployed SHAs, the profile revision, the issue's summary, description and acceptance criteria, its merged PRs) and re-probe its preconditions, then `node "…/gate.mjs" decide --gate <G> --key <KEY> --current <file>`. Any key answering `ask` (unanswered, provided but still missing, inputs changed, a key not in `G`) → re-plan those keys with `--plan`, merge every key into a new gate with `--carry <G>` (answers stay only for keys whose fingerprint did not change) and ask again as above. Otherwise continue: a `run` key goes to step 6; a `skip` key gets outcome `deferred`, reason `precondition-skipped by <who>`, and no transition.
6. **Move to QA.** For each target not yet in the qa state, pick from the transitions the issue offers the one whose target state ID is the profile's qa state. Its ID differs from `toQa` → no transition, blocked `transition-mismatch`; none offered → blocked `no-transition`; never chain. Re-read the issue; only a confirmed state counts, else blocked. Keys that already have `R/<KEY>.json` (resume) skip this step and step 7.
7. **QA, one issue at a time** (the QA environment and accounts are shared; never two at once). Before each key: heartbeat; re-read the state — not in the qa state → blocked `state changed`. Then invoke
   `$local:qa-issue <KEY> qa=max env=<profile skill> transition=done mergeShas=<owner/repo:sha,…> excludeHeads=<list> excludeBases=<list> runDir=<R> decisions=<gate file>`
   with the gate file step 5.5 cleared or the requester answered, and a diff summary of the key's PRs in the brief (e.g. `env=acme-env:staging-qa`). Reduced mode for an adapter or the screenshots directory: the invocation that section gives (`qa=high`, no `transition=done`). qa-issue writes `R/<KEY>.json` and returns its path + one line. No file → re-read the state: done with a pass comment for these mergeShas → already passed; still in the qa state → invoke once more; otherwise blocked `state changed`. Still no file → not-run `no response`.
   Except for the waiting line below, a missing `R/<KEY>.json` follows the rule above. A qa-issue line with `reason=waiting for precondition confirmation` (its inputs moved after step 5.5, so its gate asks again) is an outcome, not a missing answer: that key is `not-run` with that reason and is not invoked again. When every key is done, raise the gate for those keys as in step 5.5 (re-plan them, merge with `--carry <G>` into `<G without .json>-2.json` — the next free number, since a gate file is never overwritten — and ask); the step-9 report keeps every finished key's result in `issues` and lists only the waiting keys in `nonQa`, so no key appears twice and end `deployed, QA incomplete: waiting for precondition confirmation`.
   Every `checkpointEvery` issues, post a partial report to the calling thread: counts so far + one line per finished key.
8. **Carry-over.** Open keys: tracker comment with `range` (`<before7>..<after7>`), `mergeShas`, `verdict`, `version start/end`, reason; add `carryLabel`. Reason unchanged since its last carry comment → no new comment. Pass and fail: remove `carryLabel`. Report-only: leave the label as it is. Re-read the issue after every write; a write still not visible after one retry → `deployed, QA incomplete: tracker write unconfirmed` naming the keys.
9. **Report.** Read the running version again (version end). Build `issues` with `jq -s` over the target keys' `R/<KEY>.json` files, listed explicitly (Reduced mode without a lock: the input that section gives instead); write `R/report/report-input.json` in the shape of `qa-report`'s Input — `meta` (repo, target, range, version start/end, status line; notes naming each pass without a verified done as blocked), `issues`, `links` (per key: issue, PRs, merge commits), `nonQa` (every key not QA'd, with status and reason), `preconditions` (every precondition in the run gate, each with its `key`, so the report leads with them), `bodyMentions`, `excludedPrs`, and `outcomes` = `{KEY: {outcome, reason}}` for every key (pass / fail / blocked / partial / deferred / not-run / report-only, per Outcomes; qa-report uses it for row status and counts) — and invoke `$local:qa-report R/report/report-input.json shots=<qaEnv.screenshotsDir>` (the screenshots directory from the profile; without it every screenshot is rejected). Publish per `report` to the calling thread: the summary, the live link if the report is served, and the HTML and PNG — uploading both files to the calling thread with the session's Slack file tool (e.g. slack-mcp `send_file` / `send_media`) is a valid `report` method. If qa-report returns no PNG (the headless browser could not start, the render exited non-zero, or its validation failed), still upload the HTML to the calling thread and state `PNG not rendered: <reason>` in the summary — the PNG never fails the report or changes the run's status. Then the summary channel, only when `report` names one. Confirm each post by reading it back; a failed thread post gets one retry, then a note in the summary-channel post if there is one. Write posts in operator language (screen and feature names, not code identifiers).

## Final report
- `QA complete` only when every target key is pass, fail, or report-only and every step-8 write was read back.
- A run that stopped at the precondition gate ends `deployed, QA incomplete: waiting for precondition confirmation`: the summary leads with the gap table and the question, and says which keys wait. A CD run step 1 found failed ends `deploy failed, QA not run: …` (the deploy itself failed). Otherwise `deployed, QA incomplete: <reason>`, with the exact re-run args `repo=… target=… before=… after=… env=… keys=<open keys>` on one reference line for maintainers. Never phrase the re-run as something the requester should do. Never call an incomplete run complete.
- Enumerate every key: pass / fail / blocked / partial / deferred / not-run / report-only, its reason, and links (issue, PRs, merge commits).
- Note version start/end; if they differ, say so and name the issues whose QA spanned the change.

## Continuation
Keep working in this session until every key has an outcome. An interruption (restart, tool error) is resumed by the harness's own error retry: the lock is still mine (same token and the `startTime` from this run's start post) → heartbeat, reuse `R`, redo steps 1–5; keys that have `R/<KEY>.json` take their result from it and skip steps 6–7. `R` holds this run's evidence only; carry-over lives in the tracker. Do not create a scheduler, cron job, lane, or follow-up mechanism. A Reduced-mode run without a lock has nothing to resume: it starts again from step 1. If the run still cannot finish, end with the incomplete status above.

## Hard rules
- Touch only a range whose deploy step 1 confirmed. One key failing is recorded for that key; continue with the rest.
- Never transition to done — only `qa-issue` does, under `doneConditions`. Claim a transition only after a re-read confirmed it.
- No evidence → not a pass (`qa-issue` owns the evidence rules).
- No environment literal in anything this skill writes beyond what the profile supplies; no credentials anywhere.

## Boundaries
`qa-issue` = QA of one issue, its comments, and the done transition. `qa-report` = the HTML and PNG. The environment plugin = applicability, profile, publishing details. This skill = range, admission, order, lock, carry-over, and posting.
