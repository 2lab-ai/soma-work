# soma-work features and architecture

## What is soma-work?

A multi-tenant Slack bot that turns every workspace conversation into an AI-powered coding session. Send a DM, mention in a channel, or reply in a thread — the bot reads code, reviews PRs, plans Jira issues, and writes solutions with full context awareness.

```
You:   Review this PR https://github.com/org/repo/pull/42
Bot:   [Analyzes diff, reads source, posts line-by-line review comments]

You:   Summarize issue PROJ-1234
Bot:   [Fetches Jira issue, cross-references PRs/code, generates executive summary]

You:   Optimize this function [attaches file]
Bot:   [Analyzes uploaded code, identifies bottlenecks, proposes optimized version]
```

## zworkflow plugin

The Claude Code plugin soma-work ships by default, `zworkflow`, lives in [`src/local/`](../../../src/local/).
You can install it in your own Claude Code with `/plugin marketplace add 2lab-ai/soma-work` and
`/plugin install zworkflow@soma-work`. Install, update, hooks, and a path that copies only the
`using-intentfirst` and `using-ssot` skills are in the [zworkflow plugin README](../../../src/local/README.md).

zworkflow is meant to stay portable. The session task card calls (`GET_SESSION` / `UPDATE_SESSION`) and the NEEDS YOU
follow-up live in a second plugin, `local` ([`src/local-harness/`](../../../src/local-harness/)), which soma-work bundles and
loads by default and the marketplace never publishes; the other soma-work-only calls still in zworkflow
(`ASK_USER_QUESTION`, `CONTINUE_SESSION`, cron) move there in #860. Its `local:auto-es` is the Executive Summary inside
soma-work: it runs `zworkflow:es`, then syncs the task card, and the turn-end summary runs its turn-end contract.

## ✨ Key Features

### 🔀 Automatic Workflow Dispatch

The bot classifies user input and routes it to the optimal workflow — no manual selection needed.

| Workflow | Trigger | What Happens |
|----------|---------|--------------|
| **PR Review** | GitHub PR URL | Full code review with inline comments |
| **PR Fix & Update** | `fix` + PR URL | Implements fix, commits, pushes |
| **PR Docs** | `document` + PR URL | Generates Confluence documentation |
| **Jira Planning** | Jira issue + `plan` | Task decomposition & work breakdown |
| **Jira Summary** | Jira issue + `summary` | Executive report generation |
| **Jira Brainstorming** | Jira issue + `brainstorm` | Idea divergence & synthesis |
| **Jira → PR** | Jira issue + `create PR` | Auto-creates pull request from issue |
| **Deploy** | Deploy-related request | Deployment workflow orchestration |
| **Onboarding** | New user / `onboarding` | Interactive guided setup |
| **Default** | Everything else | General-purpose coding assistant |

Additional session-handoff entrypoints (`z-plan-to-work`, `z-epic-update`) exist for z controller handoffs (#695) — they enter via `CONTINUE_SESSION` handoff, not free-text classification. Source of truth: `WorkflowType` in [`somalib/model-commands/session-types.ts`](../../../somalib/model-commands/session-types.ts) and `VALID_WORKFLOWS` in [`src/dispatch-service.ts`](../../../src/dispatch-service.ts); prompt files live in [`src/prompt/workflows/`](../../../src/prompt/workflows/).

### 🎭 Genius Personas

Switch the bot's personality and reasoning style. Each persona brings a distinct approach to problem-solving.

```
/z persona set einstein    → First-principles physics thinking
/z persona set linus       → Ruthless code review, no BS
/z persona set feynman     → "If I can't explain it simply..."
/z persona set vonneumann  → Mathematical precision
```

Available: `default` · `linus` · `buddha` · `davinci` · `einstein` · `elon` · `feynman` · `jesus` · `newton` · `turing` · `vonneumann` — source of truth: [`src/persona/`](../../../src/persona/)

### 🔌 MCP Tool Ecosystem

Connect any MCP-compatible server (stdio/SSE/HTTP) to extend Claude's capabilities infinitely. Built-in statistics tracking and estimated completion times.

### 🔐 Interactive Permissions

Slack-native button/form UX for permission approvals, option selection, and session management. Bypass mode available for trusted users.
**Someone else's instruction waits for the owner.** When a person who is not the session's owner sends an instruction into the owner's work thread — a Slack reply, a dashboard message, or a queued note — it does not run. The thread says it is waiting, and the owner is asked by Slack DM and on the dashboard card (NEEDS YOU), like a permission request. The owner answers on either surface, and either answer resolves both: **✅ 승인** runs the held instructions once, **🔁 이 세션에서 항상 승인** runs them and stops asking for that person in this session, **⭐ 이 사람의 지시 항상 승인** runs them and adds the person to the owner's always-approve list, and **🚫 거절** drops them and tells the thread. An approved instruction runs as the person who wrote it. The always-approve list is in **⚙ 설정 → 권한 → 항상 승인하는 사람**, where the owner can remove people (people are added only from an approval request). A request waits 24 hours; more words from the same person join it. Store: `DATA_DIR/instruction-approvals.json` (`src/instruction-approval.ts`).
In every mode a non-admin session writes files only where its sandboxed shell may: the native `Write` / `Edit` / `NotebookEdit` tools, new git worktrees and switches of the working directory (into a worktree, or a subagent's) are held to the working directory and the user's own temp directory, like Bash, and `Artifact` saves only into its own scratchpad (`out_dir` is refused). A symbolic link the session puts on the way to those directories does not move that boundary (native writes stop until it is removed), and two spellings of one directory (`/tmp` and `/private/tmp`) count as one place.

### 📎 File Analysis

Upload images (JPG/PNG/GIF/WebP), text, or code files directly in Slack. 50MB limit per file.

### 🆕 Start a task from the dashboard

The dashboard's **New task** button (top bar on desktop, `Ctrl+N` shortcut (`⌃N` on a Mac); floating button on phones) opens a composer: model and effort in one model menu (each model's window, auto-compact point and cost, and only the effort levels that model runs; a shared-pool quota battery beside it), Slack channel, per-task `autogoal` and `autoz` toggles, the instruction, and attachments — files, pasted screenshots, the phone camera and voice notes. The instruction holds up to 12,000 characters: a paste that would take it past that is attached as a text file (`pasted-text-<date>-<time>.txt`) instead of going into the field, and the session reads the whole file. Beside the voice note's mic sits 받아쓰기 (live dictation, a pencil): what you say appears in the field as text while you speak, through the browser's own speech recogniser — on the device where the browser can (Safari on iPhone and Mac; desktop Chrome when Korean is installed on it), and the phone's own recogniser on a Galaxy (Chrome and Samsung Internet use Google's speech app on the phone). There the new task opens already listening, and a key typed stops it so the typing goes on. Desktop Chrome without Korean installed opens with it off; the first press starts it, and the status line says the voice goes to the browser's speech service. If the recogniser fails, the red error line says why — on a Galaxy, which setting to turn on (Google's speech app, the browser's mic permission) — including a recogniser that never opens the microphone. Three sessions in a row without words stop it; when sound was heard, the status line says what to try if that keeps happening. The session panel's message box has the same 받아쓰기. Browsers without a recogniser (Firefox, an iPhone Home Screen web app) keep the voice note only. **Settings › 받아쓰기** chooses the engine for this device — kept in this browser only, never on the server — and shows what this device's own recogniser is: browser and system, where it processes speech, Chrome's on-device model per language (with its download), the microphone permission and WebGPU; **말해서 시험** listens for eight seconds and reports the time to the first word. With **서버 위스퍼** chosen, the microphone streams to the server's Whisper (large-v3-turbo; mlx-whisper on the GPU on Apple Silicon) and the words grow every half second, settling as two transcriptions agree and at each pause — no Google speech service involved, so it works the same in Samsung Internet, Safari and Firefox; the server needs the A2T worker (`services/a2t/requirements.txt`). With **브라우저 위스퍼** chosen, Whisper runs inside the browser (transformers.js in a Web Worker, on WebGPU when there is one, else WebAssembly) and the speech never leaves the device; each device picks the model size (작게 whisper-base · 보통 whisper-small, the WebGPU default · 크게 whisper-large-v3-turbo), downloaded on first use with its progress on the status line and kept in the browser's cache. Both Whisper engines settle words with the same stream policy. Research: [`docs/misc/research/2026-11-01-on-device-dictation.md`](../../../docs/misc/research/2026-11-01-on-device-dictation.md). The task starts as your own message on a new thread in the chosen channel, so its progress is visible in Slack. The channel list is the repo-mapped channels you are a member of, plus `#workspace` at the top — the general channel, mapped to no repo, for a task that spans several repos or needs none (shown as `#workspace · 모든 repo · 일반 작업`); it defaults to the channel you last gave a command in. An admin (`ADMIN_USERS`) also sees **＋ 새 repo 채널 만들기** while the bot holds `channels:manage`: type a GitHub repo (`owner/name` or its github.com address) and the task starts in a new public channel named `workspace-<repo>` (editable; private too when the bot holds `groups:write`) — the bot makes it, writes `https://github.com/<repo>` as its description (which maps the channel to the repo), invites you and posts the task there. A repo the bot cannot read on GitHub is refused, and a repo that already has a channel gets that channel instead of a second one. Turning `autoz` on appends `$autoz` to the instruction. Pressing 작업 시작 closes the composer at once and empties it for the next task; the board shows the launch as a 시작 중 card at the top of RUNNING until the task's own card arrives. The launch toast's 카드 열기 — or a press on the 시작 중 card — opens that card on the board with its detail panel, as soon as it is there (Slack에서 보기 is the link to the thread). Launches made in a row from one page are sent one after another (the server takes one at a time per user, so a launch from a second tab at the same moment is refused and comes back like any failed launch); each shows its own 시작 중 card meanwhile. A launch that does not start leaves the board, and its instruction and attachments go back into the composer with the reason — or, when the composer holds another instruction, it stays on the board as a 시작 실패 card in NEEDS YOU until a press takes it back.

### 🧭 Plan mode

The new-task composer has a **작업 계획** (plan) switch, on by default, for every new task (each one is a Slack thread in the channel you pick). It sits at the composer's bottom right, just left of the **작업 시작** (start task) button, drawn as day and night: turn it on and the moon rises, two stars come out, the send button turns night and its label rises as **계획 시작** (start plan); off brings back the sun and **작업 시작**. On a phone narrower than 375px the send button keeps only its arrow. With it on, the task does not run straight away, and autogoal and autoz are off for it. It first fixes the instruction as given (SSOT), works out the intent (INTENT-FIRST) and writes a whole plan: the one-line conclusion and intent, a map of the phases, each phase's steps, and each step's detail — drawn by the server as HTML. This is for instructions that are expensive to misread, such as dictated or spoken ones and long epics.

- Opening the card shows the plan at once in the detail card's 입력 필요. The status bar at the top has **시작** (start) and **취소** (cancel); the bar above the composer at the bottom has **시작**, **취소** and **직접 입력** (direct input); the open task card has the same three. A card whose plan arrives opens by itself once.
- **시작** starts only the revision you were looking at (a newer one meanwhile is refused with a note to look again); the plan goes in as the next instruction and the work begins. **취소** closes the plan; a new instruction plans again. **직접 입력** goes to the composer: what you send there makes the model revise and submit the next revision.
- Until the plan is started the task has only the plan tool, never the epic's child tools. Full-page view: `/dashboard/plan/<session key>`.
- In a Slack thread, the thread gets a note with the card's link when a plan is ready. **시작** sends the plan into the thread as your next instruction, as its own turn: if a turn is still running, the plan waits in the queue behind it. A message you write in the thread while the plan waits is direct input; `/compact` and the bot's own continuation turns are not, and leave the plan waiting.
- A simple question (2–4 short choices — yes / no, start / cancel) shows its choices as buttons on the task card: one press answers it.
- **시작** also sets a goal for the plan: finish every phase. The goal loop then keeps the task going turn after turn until the plan is done, and picks it up again after a restart. Your own instruction or answer resets its continuation budget.

### 🗂️ One kind of work session

Every task is a Slack thread, whether it starts from a channel or from the dashboard's composer, and the dashboard is one view of it. Everything a Slack session does — the follow-up queue, `!` steering, goals, resuming after a restart, compaction — works on every task. The separate Slack-less dashboard task is gone (#855): a saved one is archived when the bot loads its sessions and stays readable in the board's closed column. `/z taskentry` and its setting are gone with it; an old setting is ignored.

### 🖼️ Dashboard Artifacts

Every file the model sends to Slack (HTML reports, PNG, WAV/voice, video, PDF, text) shows up in the web dashboard, newest first: as chips on the session card, a thumbnail strip in the opened card, and a strip in the session panel's common surface with each answer's own files under it. A markdown answer is the chat's — it is never listed as an artifact. Hover for a minimap preview, click for a viewer that fits the file (an HTML page, picture, video or PDF fills the screen; a document takes the full height; audio is a small dialog — HTML runs sandboxed; audio plays straight from the card). Press ‹ n / m › at its foot to pick any file of the session from a list. Uploads made before the feature are backfilled from the session's work log. A URL the session made — a page or app it serves on this machine, a video it published to YouTube — is an artifact too when the model posts it with slack-mcp `send_link`: it is listed as 링크 with its host, and pressing it opens the URL in a new tab. slack-mcp is on every Slack turn, the first turn of a session included, so videos, audio and links sent there are listed (before 2026-11-09 a first turn had no slack-mcp, and media it sent by other means never showed). One visual is one artifact: `local:html`, `local:dimensional-drawing` and `qa-report` upload the HTML only and make no PNG (the page is checked in a headless browser with `render.mjs --check`); `local:architecture-diagram` and the `diagram` router upload the PNG and keep the `.excalidraw` source local unless asked; `dimensional-drawing-motion` uploads the MP4 alone.

When a turn's Executive Summary lands (about five minutes after the work finishes — the TL;DR the Slack thread head shows), the dashboard shows it too: the whole summary as an answer in the session panel's Chat, and the TL;DR in a box on the task card. The box goes with the next instruction, never shows on a sleeping or archived card, and its × hides it from that card in your browser. When an issue or PR the session created is still not complete (open, draft, unmerged, waiting on a deploy), the summary says why in a bold ⚠️ TL;DR line and ends with a ⚠️ User follow-up required section — what is blocked, who must act, the steps, how to check, what to reply. Then the user is asked what to do next — a card never waits without a question (#917): the model-run summary asks it itself, otherwise the host asks the follow-up question (three next actions, 1 recommended, then ✏️ 직접 입력), and that question puts the card in NEEDS YOU. The follow-up clears when a later summary has no ⚠️ line, or on `/new`, and its open question is taken back. Two things never get the ⚠️ line, so a finished session does not wait for them:
- **a hand-off issue** the session filed for work outside its request, which is complete once it is filed and linked;
- **a step you ended or declined**, such as "여기까지해" or "skip that".

The summary is the soma-work harness skill `local:auto-es`: the turn-end summary runs its turn-end contract, and when the model runs it (in place of `es`) it writes the same TL;DR to the card itself (`UPDATE_SESSION { executiveSummary: { tldr } }`, together with the issue/PR/document links and their state).

**Follow-up bar** (#983): when a task card is done or waiting on you, every linked issue or PR that is still open (an open or draft PR, an open GitHub issue, a Jira issue that is neither done nor dropped) gets its own line right under the card's title bar, in gradient text — at most five, then `+N more`. Press a line to read it in the artifact viewer without leaving the dashboard: the issue's title, state, labels, body and newest five comments (the card's owner and admins only; others see the card's own reference, title and state), with **Open on GitHub**. The dashboard calls the GitHub API by the link's owner, repo and number and only for the card's own links (`GET /api/dashboard/session/:key/link-embed?url=…`). When you close the viewer, the line you pressed is gone from that card in your browser; if the issue later closes and opens again, it shows again. Running, sleeping and archived cards have no bar.

### 📎 Instruction attachments in the dashboard

The files you attach to an instruction — screenshots, PDFs, text, voice notes, video — show up in the web dashboard with that instruction, not mixed into the model's artifacts. In the session panel they sit above your words (80px image tiles, "+N" past four, file cards with kind and size, voice notes play in place). The opened card's 지시 row shows them small, the card face shows a paperclip count, and a 지시 첨부 line in the panel's common surface (collapsed by default) lists every file of the session. Clicking one opens the same viewer as artifacts, paging through that instruction's files. A message you send while the model is working is recorded with its files once the model reads it. Videos and voice notes are kept too and play in the dashboard. Files the bot could not download (over 50 MB, or a failed download) still appear, with a link to Slack. Uploaded HTML, SVG and text never run in the dashboard.

### 🧾 Turns you did not type, as one line

In the session panel's conversation, its work log (작업 로그), and an open inbox card's 지시 / 응답, a turn soma-work sent on its own reads as one line under the name **System** with a gear avatar (never your name) — when, a badge and what it did — instead of the raw prompt: **자동 압축** / **압축** (`/compact`), **시스템 재시작**, **자동 재시도** (after an error), **Goal #2/10** (goal continuation), **크론** (a cron fire), **세션 갱신** (`/renew` save and load), **백그라운드 재개 #1/6** (the turn kept going because background work was still running), and **자동 입력** for any other host turn. Click the line for its facts and the raw prompt. While a compaction runs, the line shows the elapsed time against an estimate (the conversation's previous compaction, else 2m 30s) with a progress bar; when it ends, it shows tokens before → after and how long it took. Skills an instruction invoked (`$skill`, autoskills) show as badges under your words — `local:using-ssot · ≈1.1K tokens` (an estimate) — and a badge opens that skill's text. In the inbox card, a running compaction's progress and then its result stand as the 응답, and an opened row or skill stays open while the card refreshes. Older turns are read from their text; a `/compact` recorded before this change shows as **압축**, because who sent it was not kept.

### 🖥️ Web dashboard

The dashboard (`/dashboard`, sign in with Slack) shows every session as a card and lets the session owner act on it:

- **Display language (en / ko)**: Korean by default. The **EN | KO** toggle at the top bar's right end, `lang en` / `lang ko` in Slack, and the settings page's 표시 언어 row change one setting per user. It sets the language of the dashboard, the bot's text in Slack threads, and the model's answers: the first instruction of a session ends with `<display-lang>ko</display-lang>` (again after a change). The text is translated where it leaves the server (Slack Web API calls, `respond()`, the dashboard pages and JSON errors) from the English catalogs in `packages/common/src/i18n-catalog/`; `npm run i18n:extract` lists Korean strings that still need English.
- **Minimal and advanced views**: the dashboard opens in **minimal** mode. The board shows each card's mark (a check for a plain task, **EPIC** for an epic, **CRON** for a cron run), title, status and time, the task in progress and what it asks, a line of the files it made, and at the foot's right end the cost and the model as icons only — its vendor's mark (Claude, OpenAI, Grok, Gemini, or a generic chip) in the maker's colour (Claude clay, Gemini blue, OpenAI and Grok black), then an effort gauge (1–5 bars; extra high red, max a gold foil, ultra a holographic foil); the name and effort are in the tooltip and for screen readers, and the detail card names the model in its model and effort picker beside Send. The same marks lead each model in the model picker (instead of its first letter), each agent in the agent tree and each agent tab of the session panel: the main agent shows the session's model (the Main tab names it, "Opus 5.5 (1M)", not the raw id), and a subagent shows the model it actually ran; an opened card keeps its actions and what needs you; the detail card keeps its header and what needs you in its top part and gives the rest to the task list and the chat. The stats strip, LLM capacity, the CRON lane (a cron run that waits on you or runs now stays on the board), the default model and effort chips, and the board's user picker once a user is chosen step aside. **어드밴스드** in the top bar's right end turns everything below back on. The choice is saved per user (the `dashboardMode` setting, also on the settings page). Spec: [`.prd/19-dashboard-view-mode-spec.md`](../../../.prd/19-dashboard-view-mode-spec.md).
- **On a phone the content takes the screen** (narrow, or a phone held sideways): the top bar is one line — 승인, 관리자 and the board's user picker move from the bar to the board's own head and scroll with the board. In a detail card the title bar is one line of the top bar's height, and while you scroll the chat or the work log only it and the 대화 · 작업 로그 tabs stay: the status bar and the tab bar scroll out under them, switching between 대화 and 작업 로그 keeps it that way, and a tap on the title bar, its ˅ button (카드 위쪽 보이기 — shown only while you read, so a keyboard has a named way) or scrolling back to the start of the history brings them back. The composer slides away while you scroll back through the chat or the log and comes back at the very bottom; meanwhile a ^ button at the bottom right brings it back. The session's model and effort picker sits on the composer's own row, left of Send — the composer's `end` slot lays it out — and shows the maker's mark and the level there. Browser receipts: `scripts/screenshot-mobile-chrome.ts`.
- **View plans (1, 2, 3)**: what each of the six surfaces shows — the card face, the opened card and the detail card, in minimal and in advanced — follows a plan the user picks on the settings page (**대시보드 › 화면 구성안**, the `dashboardPlan` setting). Plan 1 is the default: in minimal, the face adds the PR to its foot and asks only when the session asks; an opened card keeps its links and the model switch. Plan 2 shows progress (steps, the task window, subagent tabs); in advanced it is the screen as it was before plans. Plan 3 is the leanest: in minimal a face is title, status, cost and model and the detail card's tasks fold to one line; in advanced the numbers move to the foot, the opened card keeps its controls only, and the detail card opens folded. Every plan keeps approvals, questions, Stop and the composer. Spec with the full table: [`.prd/20-dashboard-view-plans-spec.md`](../../../.prd/20-dashboard-view-plans-spec.md).
- **Surface editor (대시보드 화면)**: a settings tab where each user arranges every surface with a live preview drawn by the board's own card code. The surfaces are the task card (collapsed and expanded, set separately), the detail card, and the Slack thread header ("스레드 태스크 카드"). The detail card is edited in its zones: the title bar (what follows the time: model, cost, tokens, tok/s, context, owner, workflow — each on or off), 입력 필요 (always right under it), the tab bar (목표 · 작업 · 에이전트 · 산출물 · 세부 with their counts, every tab closed until pressed) and the bottom (chat and work log). Every item a surface can show is listed: a switch turns it on or off, a drag handle or ↑ ↓ change the order, and what always shows carries a lock. Plans 1 · 2 · 3 are presets the user edits. The task card and the detail card each pick their default preset, and "한 번에" switches both. Changes save at once, with undo and "reset this screen". By default the thread card follows the task card in Slack (owner, current task, cost, model, and the link history when the card shows its links). It can be set separately, or keep the server's `ui.threadheader` theme. Stored per user as `dashboardLayout` (`GET/PUT /api/settings/dashboard-layout`). Spec: [`.prd/21-dashboard-surface-editor-spec.md`](../../../.prd/21-dashboard-surface-editor-spec.md).
- **Task card links (연결)**: every task card shows, by default and right below the current task, the issues (Jira, GitHub) it is linked to with their states, its PRs with their merge states (열림 · 초안 · 머지됨 · 닫힘), and its wikis (Confluence, Notion and other docs). The current issue, PR and wiki come first. The states come from the Slack thread's live PR check, the link-metadata cache (refreshed in the background with a global budget; a merged PR is never fetched again) or what was recorded with the link, and a merge from any of them wins. Each chip opens its page in a new tab and does not open the card. The row is on in every preset and can be turned off or moved in the surface editor; the PR foot chip it replaces is off by default. The links are recorded from the conversation itself: the issues, PRs and wikis a user message names (every turn), the PR or issue a GitHub write just made — however it was spelled (`gh`, `gh api`, `curl`, `fetch`, a GitHub MCP tool), proposed from the call's own result and confirmed by GitHub (created, merged or closed during that turn, up to the call's result; a head branch or title the call names must be the object's); a merge or close updates the state of a link already on the card — and the ones a reply names (these never replace the current link). At the end of every turn the host also asks GitHub which PRs the session's own branches have (each git checkout under the session's directories), so a PR made any other way — the web UI, another tool — still reaches the card: one created after the session started becomes the current PR, an older one or one on a branch another session also checks out joins the history, and so do the issues it closes. Spec: [`.prd/22-task-card-links-spec.md`](../../../.prd/22-task-card-links-spec.md).
- **Board filters and sort**: every card's foot names where the work happens — the repo (the repo of its own PR or issue, else the repo its Slack channel maps to when it maps exactly one) and the channel (`#name`, `DM`, or 대시보드 for a task with no Slack thread). In the detail card the picker sits on the message box's own row, right before Send, on every screen — also while a voice recording takes the row (before Cancel and Done). On a phone's narrow row it shows the model maker's mark and the level; the model's name is in its tooltip and accessible label. - **Permission prompts**: when a turn stops on a permission prompt (the Slack "🔐 Permission Request" card — for example a Bash command that matched a dangerous-command rule), its card moves to NEEDS YOU and the card and the session panel show the same prompt: the tool, its parameters, the matched rules and **Approve / Deny / Explain / Approve & disable rule (this session)**. Only the user the prompt was raised for sees the parameters and can answer — the same rule as the Slack buttons. Slack and the dashboard answer through one path (`src/permission-prompt-response.ts`), so whichever answers first wins and the other is told it was already answered. Every prompt also shows the auto-mode AI's advice — what the call does, why it is risky, and whether to approve. A green card means the AI recommends approving. A red card means it says not to run the call, and Approve then asks a second time on both Slack and the dashboard. When the call cannot be undone — a deploy or publish (`gh pr merge`, a push to `deploy/*`, a release tag, `npm publish`, `vercel --prod`) or a destructive command (`rm -r`, force push, `git reset --hard`, `DROP TABLE`) — the prompt says so in one line, the dashboard card approves it by sliding instead of a click (⌘↵ does not approve it), and Slack's Approve opens a confirm dialog first (a red card keeps its own second question instead). This changes only how Approve looks on a prompt that was already raised: it raises no prompt and blocks nothing, so a deploy the user told the agent to run, or any call in bypass mode, runs as before. Classifier: `somalib/permission/irreversible.ts`. Every answer is recorded in the session's 작업 로그 as a badge row (권한 승인, 권한 거부, 설명 요청, 2차 확인 승인). - **Pausing a goal**: `goal pause` (or ⏸️ in the `goal` list, or the dashboard goal card) sets the current goal aside and the session moves on: the next queued goal starts, or, with nothing queued, the goal work ends. A turn already running finishes first. `goal resume [n]` (▶️ in the list, 재개 under the dashboard card) brings back the last (or n-th) paused goal: with no goal running it becomes the current goal and starts at once; with a goal running it goes right after that goal. The answer route is `POST /api/dashboard/admin-approvals/answer` (a Slack-signed-in admin with `X-Admin-Mode: on`; auth and CSRF). The registry is `src/admin-approvals.ts`: one adapter per kind over that kind's existing request store. A question the agent asks with `ASK_USER_QUESTION` and `audience: 'admins'` (#1070) shows there too. Its card carries the question, its choices and its thread. An admin's answer to such a question is not held for the session owner. The turn it starts still runs as the session's owner, with the owner's own permissions, and the thread names the admin who answered. - **Star and revive**: **☆ Star** — the star toggle at the top right of every card face, or the button on the opened card and in the session panel — pins a session. ### 🤖 Multi-Agent Architecture

Run multiple independent AI agents within a single process. Each sub-agent is a separate Slack App with its own persona, system prompt, and session isolation.

```
@soma          → Main bot (제갈공명 persona)
@soma-jangbi   → Code review specialist (장비 persona)
@soma-gwanu    → DevOps & infrastructure (관우 persona)
```

- **Direct mention** *(pending)*: sub-agent apps connect via Socket Mode and receive @mentions/DMs, but handling is not yet wired (see TODO in `src/agent-instance.ts`)
- **Delegation** *(partial)*: main bot reaches agents via the `agent_chat` MCP tool; Claude SDK query integration is still a placeholder
- **Zero-config scaling**: Add agents by editing `config.json` — no code changes needed
- **Error isolation**: One agent crashing doesn't affect others

> **Note**: multi-agent integration is partial. The agent MCP server ([`packages/mcp-servers/agent/`](../../../packages/mcp-servers/agent/)) exposes `agent_chat`/`agent_reply` and routes to configured agents, but the actual Claude SDK query integration is still a placeholder (see TODO in `agent-mcp-server.ts`). Direct @mention/DM handling on sub-agent apps is likewise pending full `SlackHandler` integration (see TODO in `src/agent-instance.ts`).

Status and architecture note: [Sub-Agents](../../../docs/misc/guides/how-to-new-agent.md). It is **not** setup instructions — there is no supported path for provisioning an additional sub-agent today, and `somawork setup` creates the profile's primary Slack app only.
