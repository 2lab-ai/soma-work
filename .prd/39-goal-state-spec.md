## 1. 지시

원문은 [goal-state/ssot.md](goal-state/ssot.md) SSOT_2: goal 관련 비슷한 버그가 계속 난다 → goal 코드 전체를 리팩토링·폴리싱,
숨은 상태머신을 찾아 명확한 상태로 처리. SSOT_1(재시작 뒤 도는 턴이 '완료·대기'로 보임, PR #1458)은 이 계열의 한 사례다.

## 2. 목표 · 비목표

목표

- G1 — goal의 상태 하나하나가 이름 있는 타입으로 존재한다. 필드 조합이나 집합 소속으로 추론하지 않는다.
- G2 — 각 상태는 한 모듈이 소유하고, 그 상태를 바꾸는 길은 그 모듈의 전이 함수뿐이다(계약 테스트가 직접 쓰기를 막는다).
- G3 — 같은 질문에는 한 함수가 답한다: "턴이 도는가", "루프가 지금 무엇을 하는가", "주인에게 무엇을 묻고 있나",
  "이 세션의 재시작 복구는 어디까지 왔나".
- G4 — 38 §3의 버그 X1–X19를 고친다. 각각 인수 시나리오 하나로 고정한다(§6).
- G5 — 기존 goal 테스트는 모두 통과한다(동작 보존). 동작이 바뀌는 곳은 §5 결정에 적은 곳뿐이다.

비목표

- 평가 프롬프트·판정 기준, cap 기본값, 연속 턴 문구 같은 goal의 "정책"은 바꾸지 않는다.
- 누가 goal에 손댈 수 있나(주인 규칙 4가지, 38 인벤토리 D S5)는 권한 문제라 `rules/permission.md`의 수렴 작업으로 넘긴다.
- Lean 모델(T2)은 만들지 않는다. 대신 전이 표를 그대로 돌리는 표 테스트를 둔다.

## 3. 다섯 개의 명시 상태

### S1 — 턴 점유 (런타임, 저장 안 함)

"이 세션에서 지금 턴이 도는가"의 답은 하나다.

```
turnHeld(key) = 팔로업 슬롯이 잡혔다(이동된 슬롯 포함) ∨ 요청 컨트롤러가 있다
```

- 가장 이른 시계(슬롯)와 컨트롤러를 함께 본다. 슬롯은 디스패치가 받아들여진 순간 잡히고, 컨트롤러는 세션 초기화 뒤에 생긴다.
- `activityState`는 **표시용**이다. 게이트로 읽지 않는다. 턴 런타임만 쓰고, 재시작 로드 때 한 번 정리한다(D3).
- "주인 질문이 열렸나"는 별도 질문이다: `ownerQuestionOpen(session)` = 행동 패널이 선택을 기다림 ∨ 질문이 걸려 있음.

### S2 — goal 위치와 수명 (저장)

| 위치 | 담는 goal의 status | 뜻 |
|---|---|---|
| 슬롯(`session.goal`) | `active` | 지금의 goal. 루프가 이것을 굴린다 |
| 슬롯 | `paused` = **hold** | 주인이 지금 goal에서 멈췄고, 대기열이 그 뒤에서 기다린다(D6) |
| 대기열(`goalQueue`) | `queued` | 차례를 기다린다. 승격될 때 새 실행으로 다시 시작한다 |
| 선반(`goalPaused`) | `paused` | 주인이 옆으로 치웠다. 대기열을 막지 않는다 |
| 히스토리(`goalHistory`) | `complete` | 끝났다. 슬롯에는 남지 않는다(D5) |

```
          enqueue                promote                 complete
 (new) ─────────────▶ queued ─────────────▶ active ─────────────────▶ complete(history)
   │                    ▲                   │  ▲  │
   │ activate           │ resume(next)      │  │  │ hold (cap 🛑 · 대기열 있을 때 멈춤)
   └───────────────────▶│                   │  │  ▼
                        │          pause    │  │  hold(slot) ──release──▶ active
                        └──── shelf ◀───────┘  │
                               │   resume(now) │
                               └───────────────┘
 delete: 어느 위치에서든 → 사라짐(슬롯이면 대기열 머리 승격)   clear · /new: 전부 비움(히스토리는 /new에서 남김)
```

한 `goalId`는 정확히 한 위치에만 있다.

### S3 — 활성 goal의 루프 단계 (저장, 슬롯의 `active` goal에만)

```
GoalPhase =
  | opening                           첫 턴이 받아들여졌고 아직 모델에 닿지 않음
  | running                           턴이 돌거나, 다음 턴 끝이 판정한다
  | retrying  { until, attempt, reason }   판정 호출이 일시 실패 — 시각까지 기다렸다 다시 판정
  | asking    { ask: cap{ roundId, dmRef? } | stall{ stall } }   주인에게 묻는 중. 답(또는 사람의 말)이 끝낸다
  | stopped   { why: 'judge-failed' | 'start-failed', at }   재시도 소진 · 이어하기 시작 실패. 사람의 말이 다시 연다
```

```
 opening ──첫 턴이 모델에 닿음──▶ running ◀─────────────── 사람의 말 · 답(계속) · resume · max 상향
                                   │  ▲  ▲
          판정: continue(+1) ──────┘  │  └── 재시도 시각 도래 ── retrying ◀── 판정 호출 일시 실패
          판정: complete ──▶ (S2) complete       │ 소진
          판정: 같은 실패 ──▶ asking(stall)        ▼
          판정: 한도 소진 ──▶ asking(cap)       stopped(judge-failed)
          이어하기 시작 실패 ──▶ stopped(start-failed)
```

- "판정 중"은 단계가 아니다. 판정은 프로세스 안에서만 살아 있으므로 S4(구동기)의 상태다. 재시작은 그것을 지운다.
- 한도 소진은 `asking(cap)`이다. 카운터 비교로 추론하지 않는다.
- 대기열 · 선반 · 히스토리의 goal은 단계가 없다(불변식 I2).

### S4 — 루프 구동기 (런타임, 세션마다)

```
LoopState = idle | queued{ runs } | judging{ goalId, epoch } | injecting{ goalId, epoch }
```

- `injecting`은 이어하기가 받아들여져 슬롯을 잡을 때까지만이다. 슬롯을 잡으면 S1의 턴이 된다(지금처럼 턴이 끝날 때까지 끌지 않는다).
- "루프가 곧 움직인다" = `loopState ≠ idle`. "세션이 구동되고 있다" = `driven(key) = turnHeld(key) ∨ loopState ≠ idle`.
- 재시도 타이머는 goal·에폭에 묶이고 goal이 바뀌면 취소된다.

### S5 — 재시작 복구 (부팅마다)

```
BootPhase = loading → recovering → live
RecoveryRecord(세션) = { cut: boolean, resume: none | pending | started | failed | stopped-by-person, refunded: boolean }
```

- 로드 때 종료 기록(`wasWorkingAtShutdown`·사람의 멈춤)에서 세션마다 레코드를 만든다. 그 뒤 `activityState`를 정리한다(D3).
- 복구 패스는 `recovering` 끝에 세션마다 한 번 돈다. 나중의 인계(재개가 시작 못 함)도 같은 함수를 지난다.
- 패스와 인계는 `driven(key)`로 판단하고, 사람의 멈춤과 첫 턴 대기(`opening`)를 지킨다.

## 4. 불변식

테스트는 모든 전이 뒤에 `assertGoalInvariants`로 이것을 검사한다. 운영에서는 위반을 경고 로그로 남기고 고치지 않는다.

- I1 — 위치와 status가 §S2 표와 맞는다. 한 `goalId`는 한 위치에만 있다.
- I2 — 단계(`GoalPhase`)는 슬롯의 `active` goal에만 있다.
- I3 — `asking(cap)`이면 `continuationCount ≥ maxContinuations`이다.
- I4 — goal의 뜻(목표 · 한도 · 위치 · 단계)을 바꾸는 전이는 에폭을 올리고, 에폭을 올리는 길은 하나다(재시도 창도 같이 정리).
- I5 — 슬롯의 `active` goal이 `running`이고 세션이 구동되지 않으면, 그 상태를 만든 전이가 루프를 깨운다(구동 의무).
  예외: 턴이 그 상태를 만들었고 그 턴의 끝이 루프를 깨우는 경우.
- I6 — 루프는 `turnHeld`인 동안 판정을 시작하지 않고 이어하기를 넣지 않는다.

## 5. 결정

| ID | 결정 | 이유 |
|---|---|---|
| D1 | "턴이 도는가"는 `turnHeld`(슬롯 ∨ 컨트롤러) 하나로 답한다. `activityState`는 게이트에서 빠진다 | 시계 셋 중 가장 이른 것과 이미 쓰이는 것을 합친 것. X1 · X2 · PR #1458 계열 |
| D2 | 루프 게이트 = 활성 goal ∧ 단계 `running` ∧ ¬`turnHeld` ∧ ¬주인 질문 ∧ ¬호스트 대기(자동 압축 예외 유지) ∧ ¬중단 잠금 ∧ ¬종료 중 | 게이트가 cap 질문을 모르던 X4를 단계가 막는다 |
| D3 | 로드는 복구 레코드를 만든 **뒤** `activityState`를 정리한다: `working` → `idle`, 질문이 실제로 열린 `waiting`만 남긴다 | 재시작 때 훅을 건너뛰는 강제 `idle` 쓰기 4곳이 필요 없어진다 |
| D4 | "판정 중"(`pendingEval`)은 저장하지 않는다 — S4의 런타임 상태다 | 로드마다 지워지던 필드. 소유자 확인이 10곳에 흩어져 있었다 |
| D5 | 완료된 goal은 슬롯에서 내려가 히스토리에만 있다. 표면은 "최근 완료"를 히스토리에서 보여 준다 | 이중 저장(X13)과 이중 집계를 없앤다. 표면 문구만 바뀐다 |
| D6 | "슬롯의 paused"는 **hold** 하나의 뜻이다. 만드는 길은 하나(`holdCurrentGoal`)이고 남기는 필드도 하나로 같다. 첫 턴 취소는 hold를 거치지 않고 바로 지운다 | 만드는 곳마다 필드가 달랐다(38 §2.3) |
| D7 | 한도 소진 = `asking(cap)`. `goal max`는 새 한도가 카운터보다 크면 열린 cap 질문을 닫고 루프를 깨운다 | X5 · X16. #581에서 시도했다 되돌린 명시 상태를 단계로 다시 둔다 |
| D8 | 재시도 소진 · 이어하기 시작 실패는 `stopped`로 기록하고 카드에 "멈춤"으로 보인다. 사람의 말 · `goal resume`이 다시 연다 | X7. 지금은 알림만 "일시정지"라 하고 상태는 active였다 |
| D9 | goal을 바꾸는 표면은 모두 `commitGoalChange` 하나로 끝난다: 에폭 · 프롬프트 무효화 · 저장 · 대시보드 방송 · 구동 의무 | 같은 일을 하는 사본 4개(38 인벤토리 D)를 합친다. X5 · X9 |
| D10 | 되돌리기(스냅샷 복원)는 은퇴한 질문을 되살리지 않는다 — 모든 되돌리기가 같은 함수를 쓴다 | X8. 지금은 일시정지 되돌리기만 그렇다 |
| D11 | `/new` · `/renew`는 슬롯 · 대기열 · 선반을 비운다(히스토리는 남긴다). 보관은 대기열도 담는다. 봇 스레드 이동은 대기열 · 선반 · 히스토리를 옮기고, 열린 질문은 닫고 에폭을 올린다 | X10 · X11 · X12 |
| D12 | `goal resume`은 cap 또는 stall로 멈춘 goal을 다시 굴린다(cap ✅와 같은 결과). `goal done`은 이미 완료된 goal을 건드리지 않는다. Slack 🗑️는 그 줄이 보였던 위치를 보낸다. 자동 goal은 대기열이나 선반에 goal이 있으면 시작하지 않는다 | X13 · X14 · X15 · X16 |
| D13 | 복구 패스는 사람의 멈춤 이후 끊긴 세션을 굴리지 않고, 첫 턴이 남은(`opening`) goal은 첫 턴에 맡긴다 | X18 · X19 |
| D14 | 대시보드 칸은 명시 상태에서 나온다: `asking` · `stopped` → 응답 필요, 턴 점유 · 루프 동작 · `opening` · `retrying` · `running` → 진행 중, hold → 일시정지 | X17. SSOT_1이 본 화면과 같은 계열 |

## 6. 인수 시나리오

각 시나리오는 테스트 하나 이상으로 고정한다(실행 → 기대 관측). "실측"은 소유자 dev 배포 뒤 대시보드에서 확인한다.

| ID | 실행 | 기대 | 고치는 것 |
|---|---|---|---|
| A1 | 슬롯을 잡았고 컨트롤러가 아직 없는 세션에 루프를 깨운다 | 판정하지 않는다(게이트가 `turnHeld`로 막는다) | X1 |
| A2 | 재시작 인계 시점에 사람의 턴이 슬롯을 잡고 있다 | `activityState`를 쓰지 않고, 환급 · 킥하지 않는다 | X2 |
| A3 | 재시작 패스 시점에 루프가 판정 중이다 | 다시 깨우지 않고, 재개 표시를 남기지 않는다 | X3 |
| A4 | `asking(cap)` goal에 킥 · 재시작 패스가 온다 | 아무것도 판정 · 게시하지 않는다 | X4 |
| A5 | 10/10 cap 질문이 열린 goal에 `goal max 20` | 질문이 닫히고(DM 재작성) 루프가 다시 돈다 | X5 |
| A6 | 이어하기 알림을 올리는 사이 종료가 시작된다 | 이어하기를 넣지 않고 횟수를 돌려준다. "다시 보내주세요"가 없다 | X6 |
| A7 | 판정 호출이 3번 연속 일시 실패 · 이어하기 시작 실패 | 단계 `stopped`, 카드 응답 필요 + 이유. 사람의 말이 다시 연다 | X7 |
| A8 | cap 질문이 열린 goal을 지우고, 승격 goal의 첫 턴 승인이 거절된다 | 되돌린 goal에 cap 질문이 없다 | X8 |
| A9 | 재시도 대기 중 목표를 수정 · cap에 답한다 | 재시도 창이 사라지고 루프가 바로 판정할 수 있다 | X9 |
| A10 | goal A + 대기 B에서 `/new` 후 재시작 | B가 승격되지 않는다(대기열이 비었다) | X10 |
| A11 | 대기 goal이 있는 세션을 보관했다 되살린다 | 대기 goal이 그대로 있다 | X11 |
| A12 | 대기 · 선반 goal이 있는 세션이 봇 스레드로 옮겨진다 | 모두 옮겨지고 열린 질문은 닫힌다 | X12 |
| A13 | 평가 모델이 끝낸 goal에 `goal done` | 기록이 바뀌지 않는다 | X13 |
| A14 | 옛 `goal` 메시지의 대기 줄 🗑️를 승격 뒤에 누른다 | 409와 같은 "위치가 바뀌었다" 응답, 도는 goal은 그대로 | X14 |
