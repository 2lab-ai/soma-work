## 2. 문제 — 그날 밤 무슨 일이 있었나

2026-11-24 17:07 ~ 2026-11-25 07:57 KST, ‹고객 dev 호스트›.

- **호스트 과부하(범위 밖).** .NET 빌드 프로세스 33개 중 8개가 각 10~28GB를 썼다(RAM 64GB, swap 6GB). 22:38과 23:12 KST에
  커널 워치독 패닉으로 재부팅됐다. 같은 부하에서 Slack 소켓 워치독이 3번, 정기 배포·추가 배포가 2번 봇을 재시작했다.
- **결함 T1 — 잠금이 깨지면 봇 전체가 죽는다.** 계정 저장소 쓰기 잠금이 부하로 깨졌을 때(갱신이 늦어 다른 쓰기가 낡은 잠금으로
  보고 가져감) 아무도 잡지 못하는 예외가 나서 봇이 끝났다. 이때 돌던 모든 세션의 하위 프로세스도 같이 죽었다(17:07 · 20:48 ·
  22:17 KST). 첫 번째 뒤에는 남은 잠금 때문에 재기동이 두 번 더 실패했다.
- **결함 T2 — 오류 재시도가 "서비스 재시작"으로 보인다.** 새벽 6번(02:56~07:57 KST 매시)의 "시스템 재시작"은 재시작이 아니었다.
  그동안 봇은 23:13 KST부터 같은 프로세스였다. 계정 풀이 거부(429)해서 자동 재시도했을 뿐인데, 재시도가 재시작 복구 프롬프트
  ("The service was restarted…")로 나갔고 대시보드도 "시스템 재시작"으로 분류했다. 모델은 일어나지 않은 재시작을 믿었다.
- **결함 T3 — 목표 루프가 계정 풀의 대기를 모른다.** 계정 풀은 약 42시간 대기를 알렸지만 그 값은 1시간으로 잘리고 버려졌다.
  재시도 3회를 다 쓰자 목표 루프가 그 턴을 "끊긴 턴"으로 보고 이어하기를 써서 재시도 횟수를 0으로 되돌렸고, 3시간을 더
  헛돈 뒤 #948 규칙으로 멈췄다. 그날 밤 16개 세션이 같았다.
- **결함 T4 — 정상 답변이 거부로 오판된다.** 이 사고의 진단 보고가 본문 중간에 게이트웨이 거부문을 인용했다는 이유로 "계정 풀
  거부"로 처리됐다(2026-11-25 11:18 KST, ‹소유자 dev 호스트›). 답변에 Bot Error가 붙고, 1시간 뒤 같은 턴이 재시작 프롬프트로
  다시 돌았다. 판별이 본문 어디서든 매칭하기 때문이다. 사용량 한도 판별도 같아서, 오판되면 계정 교체까지 일어난다.

## 3. 목표 · 비목표

목표
- T1: 저장소 잠금 손상은 그 쓰기 한 번의 실패다. 프로세스는 살고, 쓰기는 다시 잡은 잠금 아래에서 한 번만 반영된다. 남은 잠금이
  기동을 실패시키지 않는다.
- T2: 오류 뒤 자동 재시도는 모델에게도 대시보드에도 "자동 재시도 · <사유>"로 보인다. 진짜 재시작 복구는 지금 문구 그대로다.
- T3: 계정 풀이 알린 대기(자체 상한 48시간) 동안 목표 루프는 이어하기도 #948 재개권도 쓰지 않고, 끝나면 한 번 깨운다.
  사람의 메시지는 언제나 바로 처리된다.
- T4: 본문 판별은 게이트웨이가 메시지 하나 전체로 돌려준 거부문에만 반응한다. 그 문장을 인용한 답변은 답변으로 남는다.

비목표
- 호스트 운영(.NET 동시 빌드 제한, 메모리 한도). 작업당 CPU 상한(#1418)은 관리자 세션에 적용되지 않는다는 사실만 기록한다.
- 처리 안 된 예외 하나로 모든 하위 프로세스를 죽이는 크래시 방침 자체.
- 1시간 재시도 상한의 전역 변경(one-shot dispatch 경로까지 바뀜).

## 4. 결정 (2026-11-25 trinity 3엔진 합의, 3/5 라운드 — 기록: 에픽 #1434 댓글)

- **D1 기동 시 남은 잠금: 지우지 않고 기다린다.** `init`이 `ELOCKED`를 stale 창(30초)+여유까지 같은 기동 안에서 재시도한다.
  PID 잠금은 낡은 잠금을 지우고 다시 만드는 사이에 틈이 있어 동시 기동에서 단독 소유를 증명하지 못하므로, 그 위에서 계정 저장소
  잠금을 지우지 않는다. 같은 기동 안에서 기다리므로 launchd 재기동 실패도 생기지 않는다.
- **D2 잠금 손상 처리.** 같은 프로세스 안의 쓰기를 한 줄로 세워 경쟁 자체를 없애고(1차), 손상 통지는 던지지 않고 이번 획득을
  손상으로 표시한다(2차). rename 전 손상이면 쓰지 않고 재시도 가능한 오류로 다시 시도한다. 저장소의 재시도 집합에 이 오류를 넣는다.
- **D3 본문 판별 = 메시지 하나 전체.** 다듬은 본문 전체, 또는 턴의 마지막 어시스턴트 메시지(줄이 아니라 메시지 경계)가
  1500자 이하이고 게이트웨이 모양으로 시작할 때만 참이다. 사용량 한도는 완전한 알림 문장 목록으로 시작을 본다. 오류·stderr를 읽는
  판별은 지금처럼 넓게 둔다.
- **D4 오류 재시도 전용 프롬프트.** 재시작 프롬프트를 재쓰지 않는다. 재시도 머리 + 오류 사유 + 세션 제목을 싣고, #927의
  "바깥 행동을 반복하기 전에 확인" 문단은 유지한다. 대시보드는 새 머리를 "자동 재시도"로 분류한다.
- **D5 계정 풀 대기는 소진 때 세션에 남긴다.** 알린 대기는 믿을 수 없어서(2026-11-25 실측: 알린 시각보다 약 33시간 일찍 풀림)
  1시간 탐침 3회는 유지하고, 소진 뒤에만 대기 종료 시각 = 소진 + min(알린 대기, 48시간)을 기록한다. 해제 = 성공 턴 · 사람 메시지 ·
  예약된 깨우기. 확인은 Slack 핸들러가 #948 재개권을 쓰기 전과 목표 루프 양쪽에서 한다.
- **D6 분해.** 에픽 하나 + 서브이슈 넷 + PR 넷. 네 서브시스템의 회귀 위험이 서로 독립이라 묶으면 되돌리기만 비싸진다.

## 5. 인수 시나리오

- **A1 (잠금 손상에도 생존).** 계정 저장소 쓰기 중 잠금 디렉터리를 지운다 → 처리 안 된 예외 0, 프로세스 유지, 변경은 정확히 한 번 반영.
- **A2 (두 작성자 보존).** 같은 파일의 저장소 인스턴스 둘이 서로 다른 필드를 바꾸는 중 한쪽 잠금이 손상된다 → 두 변경 모두 남고 revision +2.
- **A3 (기동 대기).** 갓 남은 잠금이 있는 채로 기동한다 → 기동이 실패하지 않고 stale 창 안에서 올라온다.
- **A4 (인용 답변 보존).** 게이트웨이 거부문을 중간에 인용한, 또는 인용으로 끝나는 정상 답변 → Bot Error 없음, 재시도·계정 교체 0,
  답변이 대화 기록에 남는다.
- **A5 (진짜 거부는 그대로).** 거부문 한 줄만 있는 턴, 서술 메시지 뒤 거부문 메시지가 따로 온 턴 → 계정 풀 판별이 참이고 지연은
  거부문에서 읽는다. 기존 사용량 한도 알림 예문 전부가 스트리밍·one-shot 양쪽에서 참.
- **A6 (one-shot 인용).** one-shot 결과가 사용량 한도 문장을 인용한 보고다 → 그대로 반환, 계정 교체 0.
- **A7 (재시도는 재시도로).** 429 뒤 자동 재시도 → 합성 턴이 재시도 머리 + 사유 + 제목으로 시작하고 "The service was restarted"로
  시작하지 않는다. 대시보드는 "자동 재시도 · 오류 뒤 자동 재개 · <사유>". 재기동 뒤 다시 걸린 재시도도 같다. 진짜 재시작 복구는
  지금 문구 그대로.
- **A8 (계정 풀 대기 준수).** 목표가 걸린 세션이 42시간 대기 통보를 받는다 → 재시도 3회 소진 → 재개권·이어하기 미소비 → 재기동을
  거쳐도 남은 시간(상한 48시간)이 지나면 한 번만 자동 재개.
- **A9 (사람 우선).** A8 대기 중 사람이 메시지를 보낸다 → 바로 처리되고 대기가 풀린다.
- **A10 (dev 실측).** ‹소유자 dev 호스트›에 배포한 뒤: 인용문이 든 답변이 Bot Error로 바뀌지 않고, 잠금을 강제로 깨도 봇 pid가
  그대로이고, 429 재시도가 대시보드에 "자동 재시도"로 보인다. ‹고객 dev 호스트›는 정기 배포 뒤 로그·대시보드만 본다(고객 환경
  배포·QA를 증거용으로 일으키지 않는다).
