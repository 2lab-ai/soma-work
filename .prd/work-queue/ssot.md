## 확정 스코프 (SSOT_1–3 승계 — loop 중 재해석 금지)

1. 큐는 soma-work 안에 하나의 체계로 둔다. 지금 있는 셋(① 배포 세션 게이트 #726, ② 환경 유저 실행 큐 v1 #1379,
   ③ deploy-qa 스킬의 잠금 대기)을 이 하나로 대신한다.
2. 큐 = 레인(지금 `deploy`·`qa`) × 환경. 레인과 환경은 `config.json`에서 더한다. ‹고객 dev 호스트›:dev = dev2·stage0,
   ‹소유자 dev 호스트›:dev = dev.
3. 줄을 서려면 키를 반드시 낸다: Jira 키(`ABC-1234`) 또는 GitHub 키(`owner/repo#123`, 이슈와 PR 같은 형식).
4. 줄 서기 전에 같은 큐에서 진행 중·대기 중인 키와 겹치는지 본다. 겹치면 들어가지 않고 겹친 키와 누가 하는지를
   돌려준다. 요청한 쪽은 그 키를 빼고 다시 들어온다. 다 겹치면 그 작업은 필요 없다.
5. 기다리는 쪽은 크론·폴링·백그라운드 대기·사람에게 묻기 없이 턴을 끝낸다. 레인이 비면 다음 차례를 시작하고 호스트가
   그 세션을 깨운다.
6. 기다리는 세션은 입력 대기가 아니라 실행 중이다. 대시보드에서 색을 달리해 큐 대기임을 보인다.
7. 모델은 큐를 MCP 하나(`work-queue`)로 쓴다. 이 MCP는 레인 종류를 모른다(일반화).

## 확정 스코프 v2 (SSOT_4–5 승계 — 위 스코프를 바꾸는 것만 적는다, loop 중 재해석 금지)

8. 개인별 큐(사람마다 동시 작업 수)와 레인 큐(QA · 배포)는 같은 코어를 쓴다: 키 · 줄 순서 · 겹침 검사 · 내역 · 보기.
   레인도 개인별 큐처럼 차례가 오면 호스트가 스스로 이어 간다. 사람이 넘기지 않는다. (SSOT_4)
9. 레인 큐는 미리 설정하지 않는다. 작업이 이름(`qa-dev2`)으로 처음 쓰면 생긴다 — 2의 `config.json` 정의를 바꾼다
   (설정은 비어 있어도 보이게 고정해 둘 큐 목록으로만 남는다). (SSOT_4)
10. 레인에서 자리를 받는 길은 둘이다: 기다려야 하는지 확인하는 try(비었으면 바로 받고, 차 있으면 아무것도 더하지 않고
    앞에 무엇이 있는지 돌려준다), 받을 때까지 기다리는 enter. (SSOT_4)
11. 관리자가 큐를 관리한다: 대기 항목 빼기 · 먼저 진행 · 진행 중인 차례 돌려놓기. (SSOT_4)
12. 작업 보드의 크론 칸 밑에 "작업 큐" 칸을 두고, 그 안에 "작업 큐 | 개인별 큐" 탭을 둔다. 큐에서 기다리는 작업 카드는
    보드 칸에서 이 칸으로 옮긴다. (SSOT_4)
13. 설정에서도 개인별 큐처럼 레인 큐를 본다: 지금 진행 · 대기 순서, 그리고 한 번에 1개씩 처리된 내역. (SSOT_4)
14. 모든 항목은 실작업 키 목록(Jira · PR)을 등록한다. 3–4는 그대로이고, 개인별 큐에도 적용한다: 같은 사람이 이미 진행
    중이거나 대기 중인 키만으로 된 지시를 다시 보내면 시작하지 않고 바로 거절한다(fast-fail). (SSOT_5)
