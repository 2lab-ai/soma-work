## 한 줄

일반 유저 모델만 샌드박스에 들어가고 어드민 모델은 밖에서 돈다. 그래서 비밀과 승인을 지키려고 별도 OS 유저 브로커를 두었다.
그 결과 환경 스킬 승인은 "스킬 글을 읽어도 된다"는 허락에 그치고, 실제 권한(GitHub 승인·머지, 환경 계정)은 따로 흩어져
GitHub 쓰기 한 건마다 어드민 카드를 기다린다.

## 1. 세 주체가 지금 받는 대우

| 주체 | 모델 실행 | 비밀에 닿는가 | 승인 |
|---|---|---|---|
| 어드민 | 샌드박스 꺼짐(어드민이 끈 설정), 봇과 같은 OS 유저 | 봇이 읽을 수 있는 것은 모두 읽는다 (봇 `config.json`의 DB 비밀번호 포함, 2026-11-12 실제로 읽힘) | 정책의 ssh · 민감 경로 · 쓰기 경계 · MCP grant 단계를 면제받는다. GitHub 비밀 · 브로커 경로 거부만 받는다 |
| 일반 유저 | 샌드박스 켜짐. 쓰기만 `/tmp/{uid}`로 묶이고, 읽기는 OS 수준에서 막지 않는다 | 봇 `.env` · `config.json`은 텍스트 검사로만 막힌다. 환경 플러그인 폴더만 OS 수준 읽기 금지 | MCP 도구는 서버마다 grant. 환경 플러그인 스킬은 어드민 4버튼 |
| 환경 (dev2 · stage0) | 주체가 아니다. 스킬 글(환경 플러그인 2개 스킬 + 어드민 개인 스킬 여러 개)과 흩어진 비밀·설정으로만 있다 | — | — |

샌드박스가 뜨지 못하면 조용히 샌드박스 없이 돈다(`failIfUnavailable: false`).

## 2. 권한 체계 8겹

1. `ADMIN_USERS` — 누가 어드민인가.
2. 어드민 `sandboxDisabled` — 어드민 모델은 샌드박스 밖.
3. `deploySandbox.users` — 배포 워크플로 샌드박스를 넓혀 줄 사람 명단. 배포 설정에 고정으로 적는다.
4. 환경 스킬 grant — 어드민 4버튼(1회 · 이 스킬 항상 · **모든 환경 스킬** 항상 · 거부). 허락하면 스킬 글을 읽게 될 뿐이다.
5. 어드민 개인 스킬의 소유자 허락 — dev2·stage0 배포·QA 스킬은 어드민 개인 스킬이라 이 흐름을 탄다.
6. MCP 도구 grant — server-tools · devops-tools, 서버마다 read/write.
7. 브로커 정책과 카드 — GitHub 쓰기·Cloudflare 단기 키는 건마다 어드민 카드(10분 만료, 대기열).
8. 게이트 없음 — github MCP. 설정에 권한 섹션이 없어 누구나 봇 App 이름으로 PR 머지·리뷰를 할 수 있다(코드 경로로 확인, 실제 시도는 안 함).

## 3. GitHub 권한의 길

- 봇 App이 PR을 만든다. 고객 레포의 통합 브랜치는 승인 1개와 리뷰 체크 2개가 필수이고, App은 자기 PR을 승인할 수 없다.
- 그래서 브로커 `gh_write`가 org-admin 계정으로 `pr review --approve`를 하고, 그때마다 어드민 카드가 뜬다.
- 배포 브랜치(dev2 · stage)에는 규칙이 없다. App이 승인 없이 바로 머지한다.

## 4. 측정된 증상 (2026-11-12, `team-host` dev)

- `gh_write` 최근 100건: 28건 1분 이상, 17건 5분 이상, 최장 20.6분 대기.
- 승인을 30분마다 확인하는 크론이 11-09·11-10에 28회 돌았다.
- 05:00 정기 작업의 봇 PR 5건이 PR마다 카드를 받았고, 어드민이 11:07 KST에 한꺼번에 결정했다. 작업 기록: "오전 일괄 — 밤새 대기 최장 4.4h".
- 배포 진입점이 둘이다. 어드민 개인 배포 스킬은 "배포 끝남 신호 → QA 레인"을 가정하는데 그 신호는 10-27에 코드에서 지워졌다. 그날 dev2 배포 4건이 QA 없이 끝났다.
- stage0 04:00 크론은 GitHub 승인 대기가 없다(배포 브랜치 규칙 0, owner = 어드민). 기다리는 곳은 QA 사전조건 게이트(사람 답)다.
- 환경 계정은 호스트 파일에 있고 QA 모델이 그 값을 직접 읽어 로그인한다. 값을 숨기라는 건 스킬 지시문뿐이다.

## 5. 브로커를 따로 만든 이유 (SSOT_2의 답)

[`16`](16-devops-tools-architecture.md) §1 위협 모델: "모델 = 봇 OS 유저의 모든 권한을 가진 공격자로 본다." 어드민 모델이 샌드박스 밖에서
봇과 같은 OS 유저로 돌기 때문에, 봇이 쥔 키는 어드민 모델이 읽을 수 있고 봇 안의 승인 기록도 쓸 수 있다. 그래서 키를 다른 OS 유저로
옮기고, 카드도 봇 밖의 브로커 전용 Slack 앱이 띄웠다. 어드민 본인 요청도 건마다 카드(D2=①).

이 판단의 전제 — 어드민 모델은 샌드박스 밖 — 를 바꾸면 브로커가 지키던 것은 한 바이너리 안에서 지켜진다. 어드민도 넓은 샌드박스에 넣으면 된다(SSOT_3).

## 6. 문서

- 환경 스킬 승인은 `.prd` 없이 PR #489(2026-10-27) 한 건으로 들어왔다. "어드민 권한으로"를 "어드민이 승인자"로 읽었고 권한 상승은 넣지 않았다.
- devops-tools는 `.prd`(14 · 15 · 16)가 있고 "gh 쓰기 = 건마다 어드민 허락"으로 확정했다. 두 설계는 하루 차이로 따로 만들어졌고 맞춰 본 적이 없다.
