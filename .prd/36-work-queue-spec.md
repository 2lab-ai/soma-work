# 36 — 작업 큐: 레인을 키로 줄 세우고, 차례가 오면 호스트가 깨운다

Status: in-progress

> 한 줄 결론: soma-work에 레인 × 환경 큐(`deploy:dev2`, `qa:stage0` …)를 하나의 원장으로 둔다. 줄을 서려면 이슈·PR
> 키를 낸다. 같은 큐에서 진행 중이거나 대기 중인 키와 겹치면 들어가지 못하고, 겹친 키와 그 주인을 돌려받는다. 줄 선
> 세션은 턴을 끝낸다. 앞 작업이 끝나면 다음 차례가 바로 시작되고 호스트가 그 세션을 깨운다. 기다리는 세션은 대시보드

> MCP 하나로 큐를 쓴다.

## 1. 지시

원문은 [work-queue/ssot.md](work-queue/ssot.md). 요지: QA든 배포든 레인이 잠겨 있으면 자동으로 기다렸다가 풀리면
이어서 하고, 사람에게 묻지 않는다. 작업마다 크론을 만들지 않는다. 기다리는 세션은 실행 중으로, 색을 달리해 보인다.
레인 × 환경 큐, 환경은 설정에서 더한다. 줄 설 때 키(Jira 키 또는 `owner/repo#번호`)를 반드시 내고, 이미 진행·대기 중인
키면 알려 준다. 큐를 soma-work에 넣고, 큐를 쓰는 MCP를 처음부터 일반화해 설계한다.

## 2. 문제 — 지금 있는 세 개의 줄 서기

2026-11-19 기준 soma-work에는 서로 모르는 줄 서기가 셋 있다. 어느 것도 키를 모르고, 둘은 사람에게 묻거나 세션이
스스로 기다린다.

| 장치 | 무엇을 막나 | 기다리는 방법 | 문제 |
|---|---|---|---|
| ① 배포 세션 게이트 (#726, `packages/slack/src/work-queue`) | `deploy` 워크플로 세션이 요청 글에서 읽은 대상 브랜치(dev2) | 세션 시작을 막고 "취소 / 다음에 배포" 버튼 카드 → **사람이 고른다**, 10분 안 고르면 취소 | 사람에게 묻는다. 메모리에만 있다(재시작이면 대기 요청이 사라진다). 글을 읽어 추측한다. 키가 없다 |
| ② 환경 유저 실행 큐 (#1379 v1, `src/slack/env-run-queue.ts`) | 같은 환경 유저의 hand-off 전부 | 호스트가 앞 실행이 끝날 때까지 다음 실행을 미룬다 | 너무 굵다(읽기만 하는 스킬도 막는다). 메모리에만 있다. 키가 없다 |
| ③ deploy-qa 잠금 (`lockDir/lock`) | 한 환경의 QA 실행 | 바쁘면 **세션이 5분마다 60분 동안** 다시 본다, 그래도 바쁘면 `lock busy`로 끝 | 이것이 "QA 레인 대기"다. 기다리는 세션은 목표 평가에 "멈춤"으로 읽혀 사람에게 묻거나, 모델이 크론을 만들었다 (2026-11-18/19, NEEDS YOU 카드 6건, 폭주 크론 2개) |

## 3. 목표 · 비목표

목표

- G1. 큐는 soma-work 안에 하나다. 큐 하나 = 레인 × 환경(`qa:dev2`). 레인과 환경은 `config.json`의 `workQueues`에서 더하고
  뺀다(재시작 없이 다음 호출부터 반영).
- G2. 줄을 서려면 키를 하나 이상 낸다. 키는 Jira 키(`ABC-1234`) 또는 GitHub 키(`owner/repo#123`)다. 다른 모양은 거절한다.
- G3. 줄 서기는 같은 큐에서 진행 중·대기 중인 항목의 키와 겹치는지 먼저 본다. 겹치면 아무것도 더하지 않고, 겹친 키마다
  그 항목(번호 · 진행/대기 · 주인 · 스레드)을 돌려준다.
- G4. 큐마다 한 번에 한 항목만 진행한다. 진행 중인 항목이 끝나면(완료 · 취소 · 자동 반납) 가장 오래 기다린 항목이 바로
  진행으로 바뀌고, 호스트가 그 항목의 세션을 깨운다(호스트 턴).
- G5. 기다리는 세션은 사람의 입력을 기다리는 것이 아니다: 목표 루프가 평가하지 않고, 후속 질문을 하지 않고, 크론·폴링이
  없다. 대시보드는 RUNNING 칸에 보라색 "큐 대기 · qa:dev2 · #2"로 보인다.
- G6. 원장은 파일이다(`DATA_DIR/work-queues.sqlite3`). 재시작해도 줄이 그대로이고, 아직 못 깨운 차례는 재시작 뒤에 깨운다.
- G7. 모델은 `work-queue` MCP의 네 도구(`queue_list` · `queue_enter` · `queue_done` · `queue_cancel`)로만 큐를 쓴다. MCP는
  레인의 뜻을 모른다: 배포도 QA도 같은 도구다.
- G8. 환경 유저 hand-off(RUN_ENV_SKILL · `$<env>:<skill>`)를 맡긴 세션은 그 실행이 줄을 서 있으면 같은 "큐 대기"로
  보이고, 그 실행의 일(줄 서기 포함)이 다 끝났을 때 결과를 받는다.
- G9. 배포 워크플로(`deploy.prompt`)와 deploy-qa 스킬이 이 큐를 쓴다: 배포는 범위의 PR 키로 `deploy:<대상>`에, QA는
  이슈 키로 `qa:<대상>`에 줄을 선다.

비목표

- 큐마다 동시 실행 2개 이상. 레인은 배타적이다.
- 호스트 사이의 큐. 원장은 봇 프로세스(호스트 · 인스턴스)마다 하나다.
- 키가 실제로 있는지(Jira · GitHub 조회), 진행한 일이 낸 키와 맞는지의 검사.
- 일부만 겹칠 때 자동으로 나머지만 넣기. 거절하고, 요청한 쪽이 다시 들어온다(SSOT_2 "취소하고 다시 큐에 들어와야함").

## 4. 쓰는 쪽이 보는 것

### 4.1 모델 — `work-queue` MCP

| 도구 | 입력 | 답 |
|---|---|---|
| `queue_list` | `queue?` | 설정된 큐마다 진행 중 1건 · 대기 목록(순서대로) · 최근 끝난 것. 각 항목: 번호, 키, 주인(유저 · 스레드), 상태, 시각 |
| `queue_enter` | `queue`, `keys[]`, `note?` | `running`(지금 시작하라) 또는 `queued`(앞에 N건, 턴을 끝내라 — 차례가 오면 호스트가 깨운다). 거절: `CONFLICT`(겹친 키와 항목) · `INVALID_KEYS` · `UNKNOWN_QUEUE`(설정된 큐 목록) · `ALREADY_IN_QUEUE`(이 스레드의 기존 항목) |
| `queue_done` | `entry` | 끝났다. 다음 차례가 시작되면 그 번호를 함께 준다 |
| `queue_cancel` | `entry`, `reason?` | 대기 중이면 줄에서 빠지고, 진행 중이면 차례를 돌려준다 |

줄의 주인은 도구를 부른 스레드(세션)다. `queue_done` · `queue_cancel`은 주인 스레드만 부를 수 있다.

### 4.2 스레드

- 차례가 오면 그 스레드에 호스트 턴이 하나 온다: 큐 · 항목 번호 · 키 · "지금 시작하고, 끝나면 `queue_done`".
- 차례를 받은 세션이 일을 하지 않고 쉬면(턴이 끝나고 5분, 사람 답을 기다리며 10분) 호스트가 차례를 돌려놓고 한 줄을
  남긴다: `⏹ 작업 큐 qa:dev2 차례를 돌려놓았습니다 (wq-17 · 세션이 일을 하지 않음). 다시 하려면 큐에 다시 들어가세요.`

### 4.3 대시보드

세션 카드가 RUNNING 칸에 있고 태그 색이 다르다.

- 대기: 보라 · "큐 대기 · qa:dev2 · #2".
- 차례를 받았지만 지금 턴이 없다(환경 유저 실행 등): 파랑 · "qa:dev2 진행 중".
- 맡긴 환경 유저 실행이 도는 중: 파랑 · "환경 작업 중". 그 실행이 줄을 서 있으면 보라 · "큐 대기 · qa:dev2 · #2".

### 4.4 설정

```json
"workQueues": { "deploy": ["dev2", "stage0"], "qa": ["dev2", "stage0"] }
```

키 = 레인, 값 = 환경 목록. 큐 이름은 `<레인>:<환경>`. 키가 없으면 큐가 없다(모든 도구가 "이 호스트에 큐 없음 —
줄 없이 진행"을 답한다). 예전 배열 모양(#726 `[{id, workflow, targets}]`)은 `workflow`를 레인으로, `targets`를 환경으로
읽고 경고한다.

## 5. 결정

- **D1. 하나로 합친다.** ①②③을 이 큐가 대신한다. ① 게이트 · 버튼 카드 · 글 추측 · `session.workQueueId`와 ②
  `env-run-queue`는 지운다. ③ 잠금은 남기되(큐 밖에서 도는 실행의 안전장치) 세션이 잠금을 기다리지 않는다.
  왜: 셋이 서로 모르면 같은 레인을 두 장치가 따로 막고, 어느 것도 "누가 무엇을 하고 있나"를 말하지 못한다.
- **D2. 줄은 모델이 키를 들고 선다.** 호스트가 글을 읽어 추측하지 않는다(①의 방식). 왜: 키를 아는 것은 일을 하는
  모델뿐이고(배포 범위의 PR, QA 대상 이슈), SSOT_2가 키 제출을 요구한다.
- **D3. 겹치면 통째로 거절한다.** 일부만 넣지 않는다. 왜: SSOT_2 — 요청한 쪽이 겹친 것을 보고 빼고 다시 들어온다. 다
  겹치면 그 일은 필요 없다.
- **D4. 원장은 SQLite 파일 하나, 바꿀 때마다 트랜잭션 하나.** MCP 프로세스(세션마다 하나)와 호스트가 같은 원장을 읽고
  쓴다. 왜: `queue_enter`가 겹침 결과를 그 자리에서 돌려줘야 한다(호스트 턴으로 나중에 알려 주면 모델이 그동안 기다리거나
  묻는다). 재시작에도 줄이 남는다(①②는 사라졌다). 처음엔 파일 잠금을 직접 만들었으나 리뷰가 오래된 잠금 탈취의 경합(PID
  재사용, 복구 경합)을 거듭 찾아, OS가 프로세스 종료 때 풀어 주는 SQLite 잠금(`node:sqlite`, metrics 저장소와 같은 것)으로
  바꿨다 — 직접 만든 잠금 · 탈취 · 백업 코드가 없다.
- **D5. 차례를 넘기는 일은 원장 안에서 한다.** `done` · `cancel` · 자동 반납이 같은 잠금 안에서 다음 항목을 진행으로
  바꾼다. 호스트는 "진행인데 아직 안 깨운 항목"을 보고 깨우기만 한다. 왜: 넘김과 반납이 한 트랜잭션이라 두 항목이 동시에
  진행이 되는 틈이 없다.
- **D6. 깨우기는 기존 호스트 턴 경로.** PR 감시 · RUN_ENV_SKILL 결과와 같은 settled delivery로, 세션이 쉬고 있을 때
  넣는다. 세션이 없거나 잠들었으면 그 항목을 반납하고 다음으로 넘긴다.
- **D7. 자동 반납 규칙(호스트).** 진행 항목의 주인 세션이 사라졌거나, 일을 하지 않으면 반납한다. "일을 한다" = 턴이 도는
  중(6시간 상한) · 맡긴 환경 유저 실행이 도는 중 · 사람 답을 기다린 지 10분 미만 · 턴이 끝난 지 5분 미만(깨운 시각 이후).
  대기 항목의 주인 세션이 사라지면 줄에서 뺀다. 왜: 모델이 `queue_done`을 잊어도 레인이 막히지 않는다.
- **D8. 기다림은 사람의 입력이 아니다.** 대기 항목을 가진 세션, 환경 유저 실행을 맡겨 둔 세션은 목표 루프가 평가하지 않고
  후속 질문을 하지 않는다. 대시보드는 RUNNING에 둔다. 왜: SSOT_1.
- **D9. hand-off의 끝 = 환경 유저 세션의 일이 다 끝났을 때.** 환경 유저의 첫 턴이 "줄 섰다"로 끝나도 요청한 쪽에는 아직
  끝났다고 알리지 않는다. 그 세션이 원장에 항목을 하나도 갖지 않게 되면 그때 `⏹`와 호스트 턴을 보낸다. 왜: G8 — 요청한
  쪽이 "끝났다"를 받고 다시 기다리거나 묻는 일이 없게.
- **D10. 키 정규화.** Jira `[A-Z][A-Z0-9_]*-[1-9][0-9]*`(대문자로), GitHub `owner/repo#n`(owner · repo 소문자). 같은 키는
  한 번만. 한 번에 50개까지.
- **D11. 이름.** 큐 = `<레인>:<환경>`, 레인 · 환경 = `[a-z0-9][a-z0-9_.-]{0,31}`. 항목 번호 = `wq-<일련번호>`.

## 6. 인수 시나리오

- **A1 (키 거절).** `queue_enter {queue: "qa:dev2", keys: ["abc"]}` → `INVALID_KEYS`, 원장 그대로.
- **A2 (바로 진행).** 빈 `qa:dev2`에 `keys: ["ABC-1", "2lab-ai/Soma-Work#12"]` → `running`, 키는 `ABC-1`,
  `2lab-ai/soma-work#12`로 저장.
- **A3 (대기).** A2가 진행 중일 때 다른 스레드가 `ABC-2`로 들어오면 → `queued`, 앞에 1건. 그 세션 카드는 RUNNING, 보라
  "큐 대기 · qa:dev2 · #1". 목표 평가 · 후속 질문이 돌지 않는다.
- **A4 (겹침).** 다른 스레드가 `["ABC-1", "ABC-3"]`으로 들어오면 → `CONFLICT`, `ABC-1`은 A2의 항목(진행)이라고 답한다.
  원장 그대로. `["ABC-3"]`으로 다시 들어오면 `queued`.
- **A5 (넘김과 깨우기).** A2 주인이 `queue_done` → A3 항목이 진행이 되고, A3 스레드에 호스트 턴 하나가 들어간다(한 번만).
- **A6 (잊은 완료).** 차례를 받은 세션이 `queue_done` 없이 턴을 끝내고 5분 → 호스트가 반납, 스레드에 `⏹` 한 줄, 다음
  차례를 깨운다.
- **A7 (사라진 주인).** 대기 항목의 세션을 닫으면 → 다음 정리에서 줄에서 빠진다.
- **A8 (재시작).** 진행 1 · 대기 1인 채로 재시작 → 원장 그대로. 재시작 전에 못 깨운 진행 항목은 재시작 뒤 깨운다.
- **A9 (설정).** `workQueues`에 `"deploy": ["dev"]`만 두면 `queue_list`는 `deploy:dev` 하나. `qa:dev`로 들어오면
  `UNKNOWN_QUEUE`와 설정된 큐 목록. 파일을 고치면 재시작 없이 다음 호출부터 반영.
- **A10 (hand-off).** 세션 S가 환경 유저 QA를 맡기고, 그 실행이 `qa:dev2`에 `queued`로 턴을 끝내면 → S에는 아직 `⏹`가
  없고, S 카드는 보라 "큐 대기 · qa:dev2". 그 실행이 차례를 받아 끝내고 `queue_done` → S에 `⏹`와 호스트 턴.
- **A11 (옛 장치 없음).** `deploy` 워크플로 세션을 dev2로 시작해도 버튼 카드가 뜨지 않는다. 환경 유저 hand-off 두 개는
  같은 환경 유저라도 동시에 시작한다(줄은 큐 안에서만).

## 7. 범위 밖

- 환경 유저 QA의 선행조건 질문(SSOT_1의 2 — 소유자가 답할 일).
- 큐 항목을 사람이 대시보드에서 직접 빼거나 순서를 바꾸는 UI(지금은 모델 도구 · 자동 반납만).
