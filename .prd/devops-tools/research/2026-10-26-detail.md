## 0. 한 줄 정의

모델은 "어느 계정·어느 환경으로 무엇을 할지"만 말한다. 키는 봇과 **다른 OS 유저**로 도는 브로커가 쥐고, 위험한 일은 브로커가
**자기 전용 Slack 앱으로** 어드민에게 확인 카드를 보내 어드민 본인의 ✅로만 실행한다. gh는 **계정별**, Cloudflare는 **환경별**(dev2 · stage0 · stage2).

## 1. 현재 상태 — 원리 (2026-10-26 실측, 호스트별 상세는 운영 저장소의 비공개 계획 파일)

- **환경 접속 도구**: 봇 배포마다 server-tools로 볼 수 있는 환경이 다르다. 유저별 grant 계층은 `config.json`의 `permission`이 있어야 켜진다 —
  없으면 `gatedServerNames`가 비어 grant 검사가 돌지 않는다(`src/agent-runtime/claude-code/build-stream-options.ts:212,227`). 조사 시점에는 켜진 배포가 없었다.
- **gh**: 봇 PR 작업의 신원은 GitHub App 토큰이다. 그러나 봇 OS 유저에 사람 gh 계정이 로그인돼 있으면, 같은 OS 유저인 모델 세션이 그 토큰을
  꺼낼 수 있다 — 조사 시점 도구 정책에는 `gh auth token`을 막는 규칙이 없었다(이번 작업에서 하드 거부 추가, 16 §2). 조직 멤버 추가·삭제에는
  `admin:org`(또는 fine-grained `Members: write`)가 필요하다(16 §9 R9).
- **승인**: 봇과 같은 OS 유저 안에서 전달·저장되는 승인·grant 기록은 모델이 쓸 수 있다 [가설: 위조 시험은 하지 않음]. **그래서 devops-tools의 승인은
  이 경로를 쓰지 않는다**(16 §5). 기존 경로의 수정은 이 작업 밖(§2 비목표, 16 §11).
- **Cloudflare**: 봇에는 Cloudflare 도구도 키도 없다. 환경마다 계정과 키가 따로 있고 봇 밖에 흩어져 있으며, 짧게 쓰고 버리는 키 체계는 없다.
- **설치 조건**: 대상 호스트의 sudo는 운영자 입력이 필요하고, 패키지 관리자로 깔린 gh·node는 봇 유저가 바꿀 수 있어 브로커가 쓰지 않는다(16 §7, `install.sh`).

## 2. 목표 / 비목표

### 목표
- **G1 키 보관**: gh 토큰·포지키·단기 키가 모델의 문맥·도구 출력·로그·Slack에 한 글자도 나타나지 않고, 모델 세션(어드민 세션 포함)이
  Bash·Read로 읽을 수 없다 — 키는 봇 OS 유저가 읽을 수 없는 곳에 있다.
- **G2 승인 무결성**: 건별 확인이 필요한 작업은 **어드민 본인이 Slack에서 단 확인**으로만 실행되고, 어드민이 본 카드 내용 = 실행 내용이다.
  모델(봇 OS 유저)이 파일·소켓·봇 토큰 어느 것으로도 그 확인을 만들거나 카드 내용을 바꿀 수 없다.
- **G3 gh**: 계정을 골라 gh 작업을 한다. 읽기 = 유저별 read grant, 쓰기 = 어드민 확인(D3), 조직·레포 권한 작업 = org-admin 계정으로만, 건마다 어드민 확인.
- **G4 Cloudflare**: 환경을 골라 작업한다. 작업 전 어드민 확인 → 포지키로 72시간 미만 단기 키 발급(그 환경의 계정·존, 승인된 권한만)
  → 그 키로만 호출 → 만료 또는 종료 시 폐기, 폐기를 Cloudflare에서 확인.
- **G5 원장**: 요청·승인·실행·발급·폐기가 브로커 원장에 남고, 봇 OS 유저는 원장을 고칠 수 없다.
- **G6 설정**: `config.json`의 `devops-tools` 섹션(server-tools와 같은 자리·같은 `permission` 예약 키). 섹션이 없는 배포는 지금과 동일.
- **G7**: server-tools의 grant 계층을 `permission` 키로 켠다(D5).

### 비목표 (v1)
- prod 환경, test2의 Cloudflare, 레포 삭제·이전·공개 범위 변경(전용 도구도 raw API 경로도 없음 — 16 §4), `gh api graphql`, 팀 관리.
- `wrangler` 등 Cloudflare CLI 실행(v1은 API 직접 호출). GitHub App 기반 gh 단기 토큰(원문이 사람 계정 다중 등록을 지정). 다른 3개 배포 설치.
- 기존 grant·허가 프롬프트의 위조 가능 구조(§1.4) 수정, 모델 세션을 봇과 다른 OS 유저로 분리하는 일 — 16 §11 로드맵으로 이름만 남긴다.

## 3. 유저 결정 (보안·비가역 — 2026-10-26 확정: 전부 1번, ssot SSOT_4)

| # | 결정 | 1번 = 추천 | 다른 선택 |
|---|---|---|---|
| D1 | 승인을 누가 검증하나 | **브로커 전용 Slack 앱**(Web API만 — 이벤트 구독·소켓 없음, scope `chat:write`·`im:write`·`reactions:read`). 브로커가 그 앱으로 어드민 DM에 확인 카드를 올리고 **어드민 명의 ✅ 리액션**을 직접 확인한 뒤에만 실행. 모델은 이 앱 토큰을 볼 수 없어 카드를 고치거나 지울 수 없다. 대가 = Slack 앱 1개 생성·설치(매니페스트 제공, 운영자 클릭 몇 번). 키 보관 O · 승인 무결성 O | ②기존 봇 토큰 사본으로 같은 리액션 방식(앱 추가 없음) — 모델도 봇 토큰을 쓸 수 있어 카드 문구 바꿔치기·원복을 막는지 라이브 시험으로 증명해야 함, 증명 전까지 승인 무결성 미확정 ③봇 경유 승인(지금의 server-tools 방식) — 키 보관 O · **승인 무결성 X**(§1.4) |
| D2 | "항상 어드민 최종 컨펌"의 적용 대상 | **어드민이 요청해도 생략하지 않음, 본인 ✅ 가능**(누르는 것 자체가 확인) | ②다른 어드민만 승인(2인 규칙) ③어드민 요청은 자동 통과 |
| D3 | 쓰기 승인 단위 | **모든 쓰기 건별 ✅**(member·org-admin 공통). 위조 불가 | ②member 쓰기는 어드민이 준 기간 write grant(편함 — 단 브로커가 요청자 Slack ID를 인증할 수 없어, 같은 봇의 다른 세션이 그 기간에 grant 보유자 이름으로 쓸 수 있음) |
| D4 | Cloudflare 단기 키 수명·공유 범위 | **기본 1시간, 요청 시 최대 71시간**, 확인 1건 = 키 1개. 키 값은 모델에 안 가고 lease ID만 간다. lease ID는 **그 봇 안에서는 소지자 권한**이다 — 같은 OS 유저라 세션을 구분해 막을 수 없으므로, 승인 카드에 "이 범위·기간 동안 이 봇의 세션이 사용"이라고 적고 그 범위로 승인받는다 | ②고정 24시간 ③호출 1건마다 키 1개(클릭이 호출 수만큼, 소지자 문제 없음) |
| D5 | server-tools grant 계층을 지금 켜나 | **예** — 4개 배포 `config.json`에 `permission` 추가(read: list·list_service·list_stack·logs, write: 쿼리 4종). 기존 사용자는 grant 요청 필요. 이 grant가 §1.4 이유로 위조 가능한 1차 문턱이라는 사실은 운영 원장에 남긴다(고객 채널 공지에는 방법을 적지 않음 — 16 §10.2) | ②`work-m64` dev만 ③안 켬 |
| D6 | 봇 유저 gh의 사람 계정 정리 | **`work-m64`·`work-m16`에서 로그아웃**(봇 전용 유저, App 토큰 사용 확인 후). `fable-m5max`는 운영자 본인 로그인 유저와 같아 유지하되 그 봇에는 devops-tools를 설치하지 않고 위험을 원장에 남김(정책 훅의 `gh auth token` 하드 거부는 코드라 다음 배포를 받는 배포마다 실린다) | ②3곳 전부 로그아웃(운영자 본인 gh 작업에 영향) ③`work-m64`만 |

해석 고정(질문 아님, 근거와 함께 진행): 원문 "디폴트는 읽기 전용으로 사용할 수 있고" + "서버툴처럼 유저별 퍼미션을 허락 받아야함" →
읽기도 유저별 read grant가 필요하다(서버툴과 같음). 주의: grant 계층이 켜진 서버에서 `permission`에 없는 도구는 공개가 아니라 **거부**된다
(`src/claude-handler.ts:2112-2114` deny-by-default) — grant 없는 읽기는 이번 범위에 없고, 원하면 별도 정책이 필요하다.

## 5. 유저 선행 작업 (구현 중 해당 지점에서 요청 — 각 1회)

1. **Cloudflare 시험 먼저 — 구현 전**(16 §6 WU0): 환경 1곳(dev2 권장)에서 포지키 1개 — 계정 소유 토큰, 권한 `Account API Tokens Edit`만.
   세 질문(필요한 DNS 자식 발급 가능? 다른 계정·존 발급 차단? 같은 계정 안 더 강한 권한 발급 가능?)의 답을 보고한 뒤 stage0·stage2 포지키.
   환경 경계가 닫히지 않으면 계획으로 돌아와 다시 확인받는다.
2. **브로커 전용 Slack 앱 생성·설치**(D1=①): 매니페스트를 드린다 — 고객 워크스페이스에 앱 1개 설치(토큰 입력은 4번 설치 자리에서 한 번에).
   워크스페이스가 커스텀 앱 설치를 막으면 D1=②로 가되, 16 §10.6 라이브 시험을 통과한 뒤에만 연다.
3. org-admin 계정 토큰 재발급: classic이면 `admin:org` 추가, fine-grained면 조직 `Members: write` + 레포 `Administration: write`.
4. `work-m64`에서 sudo 1회: 브로커 OS 유저·LaunchDaemon·루트 소유 설치(16 §8). 같은 자리에서 브로커 앱 토큰·gh 토큰·포지키를 브로커 입력 명령에 붙여넣는다(stdin 전용, 채팅 금지).
5. member 계정 = `<member 계정 메일>` 여부 확인.
